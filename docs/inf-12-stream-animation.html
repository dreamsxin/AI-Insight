01错位

两套不同的切法

token 是模型的单位，字符是人的单位。它们不重合。

后端发出的 chunk（token 粒度）
今天天气很好，适合

一个 chunk 可能只有半个汉字、半个 emoji、半个标签。

前端要的字（UTF-8 字符）
今天天气很好，适合

用户看到的是完整字符，中间不能出现乱码方块。

所以流式解析的第一个动作不是"找关键字"，而是“把字节补齐”。
02补齐

差一个字节，就先扣着

不完整就缓冲，等下一个 chunk 凑齐再交出去。

chunk 1
今E4BB8AE5← 只有 1 个字节
chunk 2
A4A9天

buffered 的 E5 等到 A4 A9 到齐，才拼成一个完整的"天"。
宁可晚 20ms，也不吐半截乱码。

这一步很不起眼，但它是所有流式体验的地基。
03状态机

一条流，三个区段

解析器要一直记得"我现在在哪一段"。

每遇到一个分隔标记，就换一个状态；换了状态，后面的内容归属就变了。

状态必须跨 chunk 保存 —— 因为标记本身也可能被切开。
04增量

标记被切开，进度留在原地

不用回头重扫，只保留"匹配到第几个字符"。

chunk 1</th
chunk 2ink>
chunk 3今天…
匹配进度：6 / 8 个字符不回头，不重扫

如果每个 chunk 都把已收到的文本从头找一遍，
长回答会越跑越慢（平方级）。

增量匹配让解析成本变成线性：每个字符只看一次。
05身份

还是那个"身份证"问题

模型自己拼出来的结束标记，不算结束。

✅
特殊 token ID 命中

解析器切换状态，后面的内容归到"正文"。

🚫
普通 token 拼出的字面量

原样保留为正文。模型可以"谈论"这个标记，但不能"使用"它。

这一条和 03 集是同一个机制的两端：进来时防注入，出去时防误判。
06工具

参数边生成，边变成 JSON

不必等整个参数拼完，再序列化一遍。

<|DSML|tool_calls> get_weather {"city": "北京", "days": 3
工具名已发出参数片段 2 个未构造完整对象

字符串逐段转义；数组和对象原样输出。
用户能更早看到第一个参数片段。

"边生成边返回"是流式的本质：不要在最后一刻才交付。
07闭环

一次请求，到这里就走完了

回头看，它穿过了五层。

🚪
入口

三种协议归一成一段对话。

🧩
编码

模板渲染、特殊 token 验身份、并行分词。

⚡
计算

prefill 读题、decode 写字，三段机器各司其职。

💾 中间算过的 KV 被三层缓存记住 → 🎲 猜着算、只算合法的 → 最后在这里变回文字
整条链上没有一个环节在"思考"，但每个环节都在决定你多久能看到下一个字。
08尾声

这一季讲的是"怎么送到"

模型的能力是上限，推理系统决定这个上限能触达多少人。

📐
能省则省

缓存、重放、掩码、变长验证 —— 都在减少无效计算。

🧩
能拆则拆

E/P/D 分离、Wide-EP、分层缓存 —— 都在把瓶颈摊开。

⏱️
能叠则叠

异步调度、GDR 换入、边生成边解析 —— 都在填满等待。
