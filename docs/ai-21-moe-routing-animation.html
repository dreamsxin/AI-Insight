01 · 前向

一次打分，选八个

门控就是一层矩阵：给 256 个专家各打一分，取前 8 个，按分数加权求和。
分数怎么来的？学出来的。

隐状态7168 维
→
Wgatebf16 矩阵
→
256 分sqrtsoftplus
→
top-8+ 归一化

每个 token 只点亮 8 / 256 格 —— 这就是「稀疏」的全部含义

所以「选谁」这件事，值得用最高精度去算：门控这一层不进 fp8 量化
02 · 塌缩

谁先跑起来，谁就一直跑

柱高是每个专家分到的 token 量。刚开始几乎一样平；
一旦有人多拿一点，它学得更快、下次分更高 —— 正反馈。

第 0 步 · 几乎一样平

塌到最后，真正干活的只剩一小撮 —— 剩下的参数白占显存，不产生能力

稀疏的前提是「大家都有活干」。一旦塌缩，MoE 就退化回一个小模型
03 · 老办法

拿损失函数拉住它

数每个专家分到多少 token，算它们的离散程度，乘一个极小的系数加进总损失。

loade = 专家 e 这一步分到的 token 数 CV² = var(load) / mean(load)² 越不均衡越大 L = Llm + α · CV² α = 1e-4
α = 1e-4
太小专家塌缩
太大语言建模变差
2.0语言建模 loss
相差
≈ 2 万倍
0.0001均衡项（CV²=1）

所以它只是「轻推」，不是「重压」—— 想靠它把负载彻底掰平，主目标就先变形了

能压住，但压的方式是「拽着走」：每一步都在和语言建模拔河
04 · 换办法

只改「选谁」，不改「给多少」

给每个专家一个偏置 b，只在挑前 8 个的时候加上去；
真正加权求和，用的还是原来的分。

专家s(x)bs+b结果

E310.405−0.010.395选中 50%

be ← be + γ · sign(mean − loade) γ = 0.001

E12 的分本来最高，被 −0.02 挤掉了。注意：入选后权重仍按 0.398 算，偏置不参与加权

b 不进梯度，所以不污染主目标 —— 模型照常学「该给谁」，只被轻轻推一下
05 · 证据

偏置跟着权重一起发布

这不是推理时的临时技巧 —— 它是训练留下的状态，写在权重文件里。

# 门控：打分用 sqrtsoftplus，选 top-k 用 noaux_tc class TopKGate(nn.Module): self.e_score_correction_bias = Parameter(zeros(256)) # 文本 self.e_score_correction_bias_vl = Parameter(zeros(256)) # 图像 self.Wgate = ReplicatedLinear(..., use_fp8_gemm=False)
🖼️
为什么要两份

文本 token 和图像 token 的专家偏好本来就不同。用一张表拉平两种分布，等于把图像往文本的均衡目标上拽。

🎯
门控为什么不量化

它只算一次矩阵乘，却决定后面 8 个专家、几十层 FFN 的算力去向。这里省精度，省错了地方。

「均衡」被固化进了权重文件：训练时算出来的表，推理时直接用
06 · 推理侧

训练调平了，请求不让

同一个专家，代码请求里热、闲聊请求里冷。
这个不平衡只能在线补：给热点专家多放几个副本，再摊到各卡。

贪心目标不是「平均」，而是让历史上最忙那张卡的负载最小 —— 木桶看短板

训练管「路由」，推理管「摆放」：同一个均衡，两个时刻，两套办法
收束

均衡是个不变量

⚖️
训练侧付两次

一次是 CV² 掺进去的干扰（万分之一），一次是每步更新偏置的符号运算 —— 都得算力，也都有代价。

📦
推理侧付搬运

加副本要显存，重排要搬权重。副本放对了是收益，放错了就是白占一份 HBM。

🔁
本质上是一直在维护

稀疏省下的是算力，买来的是一个必须持续盯着的约束 —— 它不会自己保持不变。

回看第 02 集那个「挂号台」：
现在它不光会挂号，还会自己调整每个窗口的队伍长度。

所以 MoE 的稀疏不是免费的午餐，是一份要一直续费的订阅
