STEP 1盲飞症状

两个似曾相识的深夜

Agent 开发最熟悉的两种无力感 —— 本质都是同一个缺口：没有仪表

改了 A case → 坏了 B case · 没人知道
🎯
修好一个，弄坏一个

改一句 prompt，眼前这个 case 对了 —— 上周调好的 case 悄悄坏了，没人发现

🌑
半夜挂了，无从查起

线上失败告警，但你不知道它当时想了什么、调了什么、卡在哪一步

MAST 研究测了 1600+ 条真实 Agent 轨迹：任务失败率 41%~87% ——
失败不可怕，可怕的是失败了也说不清为什么
💡 非确定性不是不测的理由 —— 恰恰是最需要测的理由
STEP 2全链路留痕

每一步都有行车记录仪

每次 LLM 调用、每次工具调用都是一个 span，串成一棵 trace 树 —— 出事能回放

run = 最小工作单元 · trace = run 树 · thread_id 串会话
TRACE · sess-8f3 · 12 runstokens · 延迟
LLMplan() · gpt-4.1 · 输入 2.1k830 tok · 1.9s
TOOLread_file("auth.ts")3.2k tok · 0.1s
TOOLrun_tests() → 2 failed1.1k tok · 6.4s
LLMfix() · 改 auth.ts:12 类型640 tok · 2.2s
TOOLrun_tests() → all pass1.1k tok · 6.1s
每个 run 记全：输入 / 输出 / token / 延迟 / 模型名 —— 失败时按下回放键，它当时干了什么一目了然（留痕原则同 Hermes 09 期审计）
💡 先有行车记录仪，再谈改进 —— 否则每次调试都靠猜
STEP 3最小评估集

从 5 个 case 开始，别等完美

评估集不是大工程 —— 是一小撮「这个样子才算对」的真实任务

改 prompt / 换模型 / 动工具 → 全量重跑
5~10 每个组件起步

挑最常见的任务，手写「好的样子」—— 一个下午的事

10~20 人工精选集

覆盖常见 + 边界场景，跑一遍扫一眼结果就算评估

+1 坏一次加一题

线上翻车的 trace 转成新 case —— 越用越准

别追求全自动大平台 —— 人工精选的小集合 > 没有评估
并排对比旧版新版，一眼看出谁退步了
💡 评估集是 agent 的回归测试 —— 小而真，胜过大而虚
STEP 4断言分层

三种判卷方式，各管一段

输出是自由文本 —— 但总有一部分可以精确判，剩下交给裁判和抽样

exact → llm_judge → human spot-check
✅
精确断言 —— 能判对错的

JSON 有某字段、文件确实改了、答案是 42 —— assert 一行搞定，零成本零争议

⚖️
LLM 当裁判 —— 说不清但能比较的

把评分标准写进裁判 prompt 打 1~5 分 —— 注意裁判也会偏：加 few-shot 示例，定期人工对表

👁️
人工抽检 —— 最后的兜底

每周抽 10 条结果扫一眼 —— 裁判失准时全靠它纠偏

能精确就精确，剩下的才交给裁判 —— 全靠 LLM 判卷等于没判
💡 断言分层的本质：把「说不清」的范围压到最小
STEP 5回归进日常

挂进流水线，坏一个就打回

评估不进 CI 就永远是「有空再跑」—— 最后变成「从没跑过」

改 prompt → eval → 全绿才许合入
✏️ 改 prompt / 换模型→ 🎯 跑评估集→ 全绿 · 合入 ✓
🎯 跑评估集→ 红了 · 打回 ✕ 定位修复
🧲 翻车沉淀循环：线上失败的 trace → 转成新评估 case → 下次同类翻车直接被拦 —— 每次事故都变成一道考题
评估集会越滚越厚 —— 这是 agent 项目唯一只涨不跌的资产
💡 让机器替你盯着回归 —— 人只处理红灯
RECAP全景

先有仪表，再踩油门

盲飞症状 → 全链路 trace → 最小评估集 → 断言分层 → 回归进 CI

没有仪表=盲飞→trace 全留痕→小评估集→断言分层→挂进 CI
🧾
先留痕再谈优化

每次调用都是 span：输入输出、token、延迟全记录 —— 失败可回放

🎯
小评估集立刻建

5~20 个真实 case + 坏一次加一题 —— 越用越准，只涨不跌

⚖️
断言分层不偷懒

能精确就精确，裁判要喂示例 —— 裁判也会偏，人工抽检兜底
