SEASON 3 · 03 · 幕 A 分数

谁说了算
什么时候不算数

同一批输出，两种判分器，两个不同的分

分数有三个隐藏参数：判分器 · 覆盖度 · 截断
向下滚动 · 一个分数是怎么被判分器捏出来的↓
01 · rule judge

零依赖的确定性判分

从模型的输出里按格式抓答案 —— 抓到什么就是什么，完全可重复

AIME 抓 \boxed{…} 里的整数 GPQA 抓 ANSWER: X 后的选项字母 i 零外部依赖 · 同一输入永远同一判定 i 推理过程完全不看 —— 只看最终格式
规则判分器又快又稳，但它只认格式 —— 格式之外的对错它看不见。
02 · LLM judge

只判等价，不看推理

自由文本需要一个「懂等价」的裁判 —— 但裁判只回答一个问题：这两个答案等价吗

R1代数等价
R2数值等价（2.0 = 2）
R3集合无序
R4单位换算
R5大小写与标点
R6多选：字母或内容
R7不给部分分
R8提不出答案算错
八条规则写死在 judge 的 prompt 里 · 除此之外不评价任何东西
边界划得很清楚：judge 不判过程对不对，只判答案等不等价 —— 推理分不在这里。
03 · 一致性

两个裁判，一个结论

AIME 的 960 条 rollout 上，rule judge 与 LLM judge
逐条比对：100% 一致

100%
960 条 rollout · 两种判分器 · 零分歧
why it matters
一致率是换裁判的通行证

正因为 960 条上完全一致，才敢说「换判分器不影响这个基准的分数」——这是可以写进报告里的验证，不是感觉。

数学题的答案足够规整，规则与模型殊途同归 —— 分歧出在下一集的自由文本上。
04 · HLE 只能用 LLM judge

自由文本，抓不出来

HLE 过半答案是自由文本。精确匹配会把「对的」判成「错的」，
系统性压低分数 —— 所以 score.py 直接拒绝 --judge rule

请求
--judge rule
→
拒绝执行
rule judge 与 HLE 不兼容
→
只能 LLM judge
等价性判断
为什么拒绝：自由文本的表面形式无穷多，逐字匹配必然误杀
判分器是跟基准绑定的 —— 换一个基准，「用什么判」的答案就变了。
05 · coverage_complete

Pass@1 只在它为 true 时有效

每道题都登记一个覆盖标志：缺 rank、缺样本，
这个题的 Pass@1 就数字作废

生成
rollout 落盘
→
判分
judge 逐条打分
→
coverage
rank/样本齐了吗
→
Pass@1
true 才计入
看起来是算分前的例行检查 —— 实际是分数合法性的裁判
一个分数成立的前提写在另一个布尔字段里 —— coverage 不为 true，一切都白算。
06 · 截断也会压分

没答完的，单独记账

finish_reason 是 length / prompt_length_exceeded 的 rollout
单列统计，不混进对错里

finish_reason处理方式
stop正常判分
length单列统计（判错但另有账）
prompt_length_exceeded单列统计
日志原话：raise the judge max_tokens and re-run i 截断多不是模型笨，是 judge 的输出预算不够
把「没答完」和「答错了」混在一格，分数就同时冤枉了两个不同的病。
RECAP · 三个隐藏参数

报分不报这三个，等于没报

判分器 · 覆盖度 · 截断 —— 幕 A 到此收口

rule / LLM judge→八条等价规则→960 条 100% 一致→coverage 闸门→截断单列
⚖️
判分器跟基准绑定

数学抓格式、自由文本靠等价性裁判；换基准先换判分器，一致率是通行证

🚦
coverage 是合法性闸门

coverage_complete 不为 true 的题，Pass@1 直接作废 —— 分数成立有前提

✂️
截断单列，不混对错

没答完是预算问题不是能力问题；混进对错会同时误诊两个病

“99.9 后面站着两个裁判、一道闸门
和一张截断名单 —— 这才是完整的分数。”
