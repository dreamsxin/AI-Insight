01 · 三种

一份 cache，三种版式

同一个模型里跑着三套结构不同的缓存。
它们不共用格式，也几乎不共用代码。

ca_cache · compressed attn
主 KV —— 每 token 一条记录

一条记录是 [数据 | scale]。per-16 FP4 时 288 B，MXFP8 时 528 B。压缩比决定一个 block 里塞几条。

ica_cache · index attn
索引 KV —— 一个字节一个分数

uint8。每条记录的条数是 block_size // ratio，比主 KV 再压 ratio 倍。它只回答"这个块值不值得看"。

swa_cache · sliding window
滑动窗口 state —— 每个序列一份

不是按 block 分配，是按序列分配。每个 token 528 B：512 B FP8 数据 + 16 B UE8M0 scale。

三种缓存，三种寻址方式 —— 这就是为什么 KV cache 的代码总是比模型代码还长。
02 · 拆开

288 和 528，差在哪

都是 512 个值。区别是：一个值存 8 位，还是 4 位。

MXFP8 · 每 32 个值一个 scale528 B
512 B 数据 · 8 bit/值
per-16 FP4 · 每 16 个值一个 scale288 B
256 B 数据 · 4 bit/值
少占 240 B
粉色那一段是 scale 本身：把数值压到 4 位，scale 的密度反而翻倍（每 16 个值一个）。
位宽减半省下 256 B，scale 变密又还回去 16 B —— 净省 240 B。
03 · 共用

不是每层都有自己的缓存

若干层通过 mapped layer id 指向同一份 cache。
层数不等于副本数。

L0L1L2L3 L4L5L6L7
8 层 ↓
cache #1L0 · L1 · L2
cache #2L3 · L4
cache #3L5 · L6 · L7
高亮的层是这份 cache 的"拥有者"，其余层指向它 · 结构示意
算容量的时候，分母是副本数，不是层数 —— 这一步算错，整套容量规划跟着错。
04 · 对齐

528 除不尽 32

搬运的最小粒度是 32 B。528 / 32 = 16.5 ——
一个 token 切不齐，两个才切得齐。

tok 0余半格
tok 0 + tok 1 = 1056 B
1056 = 33 × 32，正好齐
why align at all
不是为了好看，是为了能"一次拿一整段"

对齐之后，一个连续的块能被一条指令整段取走，不用逐条拼。所以整个 block 按 lcm(32, 528) = 1056 对齐。

代价是零头：一个 block 必须是偶数个 token，奇数就得白留半个。
05 · 分区

要落盘的往前放

一份 state block 里，需要持久化的放低地址，
不需要的放高地址。

storedSWA · 要落盘
droppedconsumer SWA · compression
写盘边界 = state_size_to_disk
the trick
不用挑着写，按长度截一刀就行

因为 dropped 区整段都在边界之后，落盘时只取前 state_size_to_disk 个字节 —— 后面的部分天然被排除，不需要逐块判断。

布局顺序本身就是一个优化 —— 把"要不要写盘"变成"写到第几个字节"。
06 · 收束

它是一种格式，不是一块内存

📐
版式

每 token 一条 [数据 | scale]，长度由位宽和 scale 密度决定：288 或 528。

🧮
对齐

32 B 是搬运粒度，lcm(32, 528) = 1056 是块粒度 —— 两个约束都来自硬件，不是设计偏好。

✂️
分区

stored 在前、dropped 在后，让"要不要落盘"退化成一个长度参数。
