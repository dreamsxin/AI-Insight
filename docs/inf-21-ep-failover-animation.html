一块卡，
拖垮整个实例

大 EP 里，所有 GPU 是一个通信域。
少一个，全组都跑不起来。

健康 故障 待重组
向下滚动↓
01通信域

EP = 大家一起做一个 all-to-all

token 发给别的卡上的专家，结果再收回来 —— 每个人都要参与。

8×8 = 64 张卡，EP64；每张卡都可能和任意一张卡交换 token。

这不是「谁坏了谁少算一点」，而是一次集合通信，缺一个人就凑不齐。
02为什么全挂

集合通信没有替补

一格红掉，整组停摆。

01
等不到

all-to-all 要每个 rank 都提交分片，缺一个，其它 63 个全部阻塞。

02
算错了也不知道

专家分布在所有卡上，少一张卡就少几个专家，路由过去没人接。

03
不能降级跑

EP size 是编译期/启动期定好的，运行中改不了。

所以「一块坏」在运维视角等于「实例级别故障」，不是单卡故障。
03重组

重启时，按手里的卡重新定 EP

不是「凑回 64」，而是「你有多少，就用多少」。

1
收集健康 GPU

重启时不假设原样恢复，先问平台「现在有哪些卡是好的」。

2
重新确定 EP size

拿到的卡数直接当 EP size，用它重新划分专家。

3
重建通信域并重新分片

专家权重按新的 EP size 重新切分与放置。

这样剩下的 63 张卡不会陪着一起躺，而是继续服务 —— 只是每人多背几个专家。
04代价

63 不是个漂亮的数

EP 规模一变，一堆配套参数都要跟着变。

红色一块已剔除，绿色 63 张卡继续跑；灰色的那一格在等它修好。

专家数要能整除 EP、冗余专家要重算、负载均衡统计要重来 —— 重组比重启贵得多。
收小结

故障这一幕的落点

🌐
EP 是一个通信域

不是一堆独立卡，而是一个整体。

💥
单卡故障 = 实例故障

集合通信没有替补机制。

🔧
按实际卡数重组

拿多少用多少，剩下的卡不陪葬。
