STEP 1全量手册的老毛病

一百本手册，不能天天背在身上

把所有工具说明书、规范、示例都塞进 system（02 期的消息开头）—— 任务还没开始，窗口先满了

技能 A 完整说明技能 B 完整说明技能 C …×30 个技能全部示例代码
每轮对话都重发一遍（Hermes 02 期：无状态设计）—— 真正用得上的往往只有 1~2 个技能，其余全是占位噪声，还会稀释模型对关键指令的注意
启动时上下文占用 →留给任务的空间所剩无几
💡 避坑 03 期的结论在此成立：上下文是稀缺预算 —— 技能说明也该按需取用，而不是全员常驻
STEP 2渐进式披露

三层：名录 → 正文 → 细节

Agent Skills（2025-07 发布）的核心机制：技能内容按相关性逐层进入上下文，像翻卡片而不是搬书柜

0 元数据名录

启动时只载入每个技能的 name + description，几十字一张「名片」

 全程常驻
极廉价
1 SKILL.md 正文

模型判断「这个技能相关」时，才读这一份说明书

 命中相关
才加载
2 引用文件与脚本

正文里引用的模板、参考文档、可执行脚本，用到哪个读哪个

 执行到
才读取
💡 这正是 RAG「just-in-time 检索」思想（避坑 03 期）在能力层的复刻 —— 资料按需读，技能也按需翻开
STEP 3一个技能包长什么样

说明书 + 素材库 + 确定性脚本

pdf-processing/
├─ SKILL.md # 正文：何时用、怎么做
├─ references/
│  ├─ color-profile.md
│  └─ font-checklist.md
├─ assets/
│  └─ template.json
└─ scripts/
   └─ fix_pdf.py
正文保持精简SKILL.md 只写触发条件与步骤大纲，细节外链到 references —— 控制 L1 的体积
脚本直接执行确定性操作交给脚本跑，输出回灌结果 —— 不占模型的推理上下文，也不会被「理解偏差」
💡 与 03 期 MCP 工具分工：MCP 接通外部世界，Skills 沉淀「怎么干好一件事」的工序
STEP 4与旧做法的对比

菜单越厚，决策越差

✕ 全量工具定义

  • 几十个工具的完整 schema 常驻
  • 选择干扰（避坑 01：菜单越短越准）
  • 加能力 = 加常驻 token

✓ 技能名录 + 按需翻开

  • 名录阶段只看到一句话描述
  • 相关才载入正文与工具细节
  • 装得上百个技能，启动仍轻盈
同一套设计也被用于 Tool Search：工具定义按需检索（5.5 万字 → 约 7.7K 名录）
—— 上百工具只占极小菜单，相关工具才「解封」
💡 Hermes 03 期的 instructions 是全量注入的 L1；Skills 补上了 L0 名录，规模差出一个数量级
