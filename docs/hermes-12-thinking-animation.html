STEP 1先回顾老循环

think 曾经只是一瞬间

Hermes 04 期的主循环：LLM 只有提案权，think → act → observe 里的 think 是一次普通采样，用完即走

while loop < MAX_LOOPS: think() → 拦截意图 → call_tool → 塞回 messages
think（一次采样）→ tool_call→ tool_result↻
普通模型：think 阶段几乎不产出「过程文字」，规划能力全部押在一次即时反应上
难题、长工具链、多约束决策 —— 一步看错，后面全错（16 期：直接答的天花板）
$ 问题：think 看不到「我为什么要调这个工具」的完整推导
$ 工具一报错，它没有地方「停下来重想」，只能立刻生成下一条消息
💡 老循环的 think 是反射 —— 推理模型要把它变成一段可长可短的草稿
STEP 2思考进入同一条消息

先想一大段，再决定调什么

2025 年起 API 支持「交替思考」：一条 assistant 消息里，thinking 块和 tool_use 块可以并存

ASSISTANT（第 3 轮）
💭 报错 ENOENT：先怀疑路径错；但工作目录在第 2 轮被 cd 改过……
   得先 pwd 确认当前目录，再决定改路径还是重建文件
🔧 tool_use: bash({ cmd: "pwd && ls -la" })
TOOL /srv/app · config.yml 不存在 …
ASSISTANT（第 4 轮）
💭 配置文件真的缺失 —— 不是路径问题，改为从模板生成，再跑测试
🔧 tool_use: edit_file({ path: "config.yml", … })
💡 思考不再游离于循环外 —— 每一轮都能「看结果 → 复核 → 再动手」
STEP 3思考插入循环的三个位置

不是每一步都要深思

工程上思考可以放在循环外、每轮前，或拿到关键工具结果后 —— 位置不同，成本天差地别

① 循环外预思考一次性规划
think → 计划清单 → 进循环照做
适合步骤已知的任务；中途易与现实脱节
② 每轮都思考最稳但最贵
think → tool → think → tool …
闲聊/简单调用上纯属烧 token
③ 交替思考 ✓在岔路口想
拿工具结果 → think 核对 → 再决策
思考与动作穿插，预算花在真正的分叉处
💡 16 期的 effort 档位在这里落地：架构师配置的不是「想不想」，而是在哪几步想
STEP 4思考也要进预算表

思考 token 是循环里的新开销

Hermes 02 期的铁律：每轮重发全量历史 —— 长思考链既拖慢又烧钱，必须像工具调用一样设闸

单轮构成
每轮思考上限 总思考预算 超支 → 降级/收尾 联动 MAX_LOOPS（避坑 02）
思考链默认不展示给用户（Hermes 10 期：静默期要占位播报），但它实打实计入输出 token 账单
高难度任务允许上万思考 token，客服快问快答则把思考预算压到接近 0
💡 repeat_guard 管步数，token_budget 管总量 —— 现在再加一道思考预算，三道闸防失控
STEP 5工程共识：何时开

开思考不是越勤越好

✓ 开思考

  • 调试排错：报错链需要假设与验证
  • 多约束规划：权限、依赖、顺序互相牵制
  • 失败后重试：拿错误当观察，换路再走

✕ 关思考

  • 闲聊、改写、格式化
  • 彼此无依赖的并行小调用
  • 实测：只增延迟与成本，不增成功率
🧠 跨轮保留：长思考在下一轮要被压缩成结论摘要进上下文 —— 原始草稿只留关键决策，否则又喂大了 02 期说的雪球（上下文工程同款手法）
💡 推理模型进 Agent，改的不是模型调用 —— 是循环的节奏、预算的口径、上下文的取舍
RECAP全景

会思考的 Agent 循环

thinking 与 tool_use 同条消息 → 在岔路口交替思考 → 思考预算进闸门 → 草稿压缩跨轮

think 草稿→tool 调用→observe→再 think→answer
🔀
思考与动作交替

thinking 块和 tool_use 块可在同一条消息并存 —— 每一轮都能先复核观察、再决定下一步

🎚️
预算花在岔路口

简单任务关思考，硬题在关键工具结果后开；思考 token 设单轮与总量上限，联动步数闸门

🗜️
草稿要压缩再传

长思考链跨轮只留结论摘要 —— 推理更强，但上下文雪球与账单仍要按老规矩管
