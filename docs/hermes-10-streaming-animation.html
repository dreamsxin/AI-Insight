STEP 1没有流式的世界

等 30 秒白屏，谁不疯

如果等全部生成完才返回 —— 用户盯着一个转圈动画，只能靠猜

非流式：一次性返回 · 全程无反馈
帮我把这个报错修一下
对方正在输入…
已等待 28.4s · 你依然什么都没看到
用户的真实心理活动：「死机了？我再点一次」 —— 于是重复发问、重复扣费、重复执行
💡 长时间零反馈，比慢更伤体验 —— 人不怕等，怕的是不知道在等什么
STEP 2本来就是逐 token

模型天生就是一个字一个字写

回忆 03 期：模型每步只采样一个 token，算完才轮到下一个 —— 流式只是把这个过程边算边发

不是「算完再切条」—— 是算一个、发一个
今天天气真好
每蹦一个字 = 后台完成了一轮「注意力 → 概率表 → 采样」（11 / 12 期）
流式只是把这趟内部流水线，原样直播给你看
💡 打字机效果不是演出来的 —— 模型真的就是这么写的
STEP 3SSE 事件流

一根管道，持续推送

HTTP 连接不再「请求—等—响应」，而是一条不断推小事件的下行流

text/event-stream · 前端收到一个 delta 就画一个字
01message_start会话开始 · 上下文就绪
02content_block_delta{"text": "今"}
03content_block_delta{"text": "天"}
04tool_use调用工具 read_file("src/app.ts")
05content_block_delta{"text": "修好了：…"}
06message_stop本轮结束 · 连接关闭
07ping保活心跳 · 防止连接被掐断
每条事件都是一行小 JSON —— 拼起来才是完整回复
💡 流式的「一整段回复」，其实是几百个小事件拼出来的
STEP 4静默期

说到一半，去干活了

Agent 不是一口气说完 —— 中途要停下来调工具，这几秒没有新 token 产生

delta 流 ≠ 匀速 —— 中间藏着工具时间
我看看这个报错……（说到一半）
🔧 正在读取 src/app.ts · 已运行 2.1s
找到了，第 12 行类型写错了，改成……
解法：状态占位 —— 工具开始/结束都作为事件推给前端
「正在读取…」「正在搜索…」让静默期变成看得见的进度
💡 Agent 场景的流式，难点不在推字 —— 在把工具时间也演给用户看
STEP 5TTFT 与中断

第一印象，是第一个字

从「发送」到「第一个字蹦出来」的等待，叫 TTFT —— 流式体验的命门

TTFT = time to first token
点击发送⚡ 首个 token持续输出
📦
上下文越长，首字越慢 —— 发送前要先「读题」（prefill），几百 KB 的窗口（02 期）能让人等到怀疑人生
🛑
随时可打断 —— 按 Esc 直接掐断请求；已经生成的一半照样有效，没生成的不再浪费
💡 优化体验先压 TTFT —— 第一个字一出来，焦虑就消失一半
RECAP全景

把等待，变成目击

逐 token 生成 → SSE 推流 → 打字机渲染 → 静默期占位 → 随时中断

逐 token 生成→SSE 事件流→打字机渲染→工具期占位→可随时打断
⌨️
打字机是真的

模型本来就是逐 token 写作 —— 流式只是把这趟内部流水线原样直播

🔧
静默期要占位

Agent 的流式不止推字 —— 工具的开始、进度、结束都是事件，全都要演出来

⚡
命门是 TTFT

压首字延迟、允许随时打断 —— 感觉快，比真的快更先被感知
