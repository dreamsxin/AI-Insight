01 · 固定成本

慢的不是算，是发号施令

每一个 kernel 都要从 CPU 派一次活。这一步的耗时是固定的，
和你让它算多少无关。

一次 decode —— 44 个 kernel
每两根亮条之间的缝隙，就是一次发射
同样的活 —— 一次发射
缝隙全部消失
算的部分一点都没少，少的是"喊开始"的次数
一个 token 几十毫秒，几百次发射就是其中不可忽视的一块。
02 · 录下来

先录一遍，之后按下播放

CUDA Graph 把整段前向的执行序列录成一张图，
之后每步只调一次 replay()。

这是一次性的开销，换来每一 token 的收益 —— 所以它只对 decode 这种"同一段路走几千遍"的场景划算。

04 · 代价

padding 会咬人

真实 batch 37 跑 40 的图，多出来的 3 行是空的。
更麻烦的是：有些地方必须知道"真正的请求数"。

🕳️
白算的 3 行

图只认识桶，不认识 37。多出来的行照样走完整前向，只是结果被丢掉。

🔢
num_reqs 必须记真实值

统计、以及上下文并行里非 driver 的 rank，都要靠它把 padding 摘出去。用桶大小当请求数，算出来的东西全错。

🧹
复用前要清理

有些字段在 forward 里会重算，复用图之前必须置空，否则拿到上一批的残留。

图给你省了发射，也拿走了"每一行都是真数据"这个假设。
05 · 共用

所有图共享一个内存池

11 张图不是 11 份显存 —— 它们共用同一个 pool。
所以捕获必须从大到小来。

graph_memory_pool

bucket 48
bucket 32
bucket 8
先录最大的那张，pool 一次长到位；后面的小图直接复用里面现成的空洞
如果从小到大录，pool 会被反复撑大、反复搬迁 —— 顺序在这里不是风格问题，是能不能跑起来的问题。
