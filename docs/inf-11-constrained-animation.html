推理原理 · 11

只能走对的路

它想写什么都可以。
但每一步，只有落在语法里的 token 才被允许。

向下滚动↓
01三种约束

给输出画一个圈

三种写法，最后都变成同一件事：某一步允不允许。

json_schema
最常用的那种

字段名、类型、必填项都写在 schema 里。

regex
一个正则

例如订单号 ^[A-Z]{2}\d{6}$，逐字符限定。

ebnf
一段文法

比正则更强，能表达嵌套结构。

不管哪种，都要先被翻译成一台会走路的机器。
02编译

schema 变成自动机

每个圆圈是一个状态，每条边是"允许写什么"。

每读一个 token，沿边走一格。
走不到的状态，那个 token 就不允许被采样。

编译一次，可以服务很多请求 —— 所以它被挪到了推理引擎之外。
03解耦

编译的不在关键路径上

schema 编译很贵，但只做一次。

专用编译机
把约束编译成自动机

异步进行，算完存起来。请求来之前就已经准备好。

推理引擎
只负责"走一步"

每步推进自动机、算合法集合、生成掩码。

编译与推理分开，意味着编译慢不会拖慢线上。
04每步

此刻，只有这些能写

自动机往前看一步，给出合法 token 的集合。

SureHere好的 { 空格" Sure!```json

划掉的是"模型很想说、但语法不允许"的 token。
划在 mask 里，不是靠事后修文本。

注意：这不是提示词里写"请输出 JSON"，而是物理上写不出来。
05掩码

把非法项的分数按到底

不是删掉，是置成负无穷 —— 采样就永远不会选中。

词表里的候选 token红色：被 mask

mask 是一个和词表等长的向量，每个 decode step 都要算一次。
所以它的开销，直接算在 TBT 里。

掩码让"合法"变成"高概率"，而不是"希望它听话"。
06顺序

先掩码，再采样

顺序反了，前面全白做。

✓先 mask，再 temperature / top_p正确
✕先采样，再检查合法性已经写出去了
✕采完发现非法，再回退重写浪费一步
采样参数照常生效 —— 约束只缩小可选范围，不改变范围内的偏好。
07走一遍

一个 JSON，一步步收窄

每写一个字符，合法的下一步都在变少。

{"name": "天…
已走 11 步 当前合法集合 ≈ 3.2 万 个 token 整词表 ≈ 12.8 万

开头第一个字符只有极少数选择，越往后越宽；
遇到引号、括号，可选集合又猛地收窄。

这也是为什么长 JSON 的 decode 会稍慢 —— 每一步都多了一次掩码计算。
08小结

最后一步：把 token 变回人话

输出合法了，但它还是一串 token。

🔁
约束即自动机

schema、正则、文法，最后都编译成状态机。

🕳️
掩码定生死

非法 token 置 −inf，采样只在合法集合里进行。

📦
编译在引擎外

贵的一次性工作挪走，线上只承担每步推进。
