01主干

一步走完的八个阶段

从「准备好元数据」到「把 KV 写回去」，每一步都是一次或多次 kernel 启动。

01准备 metadata 02norm + 量化 03按 block 取 KV 04注意力 05路由 top-k 06dispatch 07专家 GEMM 08combine 09norm + lm_head 10采样 11写回 KV

高亮的三个是真正吃算力的；其余大半时间在搬数据、拼元数据。

这些 kernel 大多不是手写的 CUDA，而是用 TileLang 一类工具生成的 —— 跑在 tilelang_ops/ 里。
02时间轴

GPU 在等什么

把一步拆成时间片，会看到大量非计算的空隙。

拆分：11 个 kernel一步 ≈ 100%
融合后：3 个 kernel同样的一步
计算 通信 空隙（启动/同步）

空隙不只是「浪费时间」，它还意味着这段时间 SM 完全空着。

融合不是为了少几次启动，是为了让数据不落回显存。
03融合

三个值得融的地方

判断标准只有一个：中间结果是不是本来就要落回显存。

RMSNorm
→ 8bit 量化→一次读出、
三套 scale 一起写
dispatch
→ 专家 GEMM
→ combine→Mega MoE：
token 不再落回 HBM
lm_head
→ 采样→logits 不写回，
直接在寄存器里采样

第三处最容易被忽略：词表有几万个，logits 写回再读一遍，就是几十 MB 的纯浪费。

下一集专门看第二处 —— 它是这三处里最难、也最值钱的。
04清单

这些 kernel 长什么样

工程里能直接看到名字 —— 一个阶段常常拆成好几个细粒度算子。

norm.pygather.py load_paged_kv_cachestore_kv_cache swa_indexget_kv_index flash_mla_utilscandidate_blocks schedule_mtp_varlenfused_sample random_samplingstructure_output prepare_v4_decode_metadataoutlier_detection

名字本身就是线索：metadata、index、schedule 这类不算数的算子，占了半壁江山。

所以「推理框架」的一大半工作，是把元数据算对、把调度排好，而不是写矩阵乘。
05代价

越碎，越贵

kernel 数量上去，有效算力反而下来。

3 个高
8 个中
20 个低

横条 = 同样的计算量下，SM 真正在算的时间占比（示意）；每次启动都有固定开销，还要重读一遍中间结果。

这就是为什么「算子级优化」的天花板，往往卡在算子之间的缝里。
