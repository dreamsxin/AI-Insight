STEP 1分层结构

一次调用，五层拼装

你只发了「帮我修 bug」—— 但发往 API 的 messages 是一座五层小塔

system → 工具清单 → 记忆 → 历史 → 本轮输入
① system

人设 + 规则：你是谁、办事边界、输出要求 —— 每轮都带（Hermes 01 期）

② 工具清单

全部工具的 schema —— 也是 token！几十个工具就是几千 token

③ 记忆

跨会话偏好 / 关键事实注入（08 期）—— 只挑相关的

④ 历史

messages 数组逐轮生长（04 期）—— 体积大头，含全部工具结果

⑤ 本轮输入

用户新消息 + 改写后的查询 —— 塔尖

每层来源不同、变化频率不同 —— 这个差异决定了缓存策略和裁剪顺序（后两屏）
💡 模型每轮「重新读一遍全文」—— 组装器决定它读到的是哪一版世界
STEP 2静态层

每轮都带、几乎不变的部分

system、工具清单、技能说明 —— 内容稳定，是缓存命中的黄金前缀

静态层放前面 = prompt cache 每轮命中
🧭
system prompt

人设、边界规则 —— 改一次全改，别在里头塞本轮才用得上的内容

🔧
工具清单（schema）

每个工具的名称、描述、参数定义 —— 数量即成本，按任务挂载（dev-01 期）

⚡
缓存黄金区

静态层放在最前面且逐字节不变 → 厂商 prompt cache 每轮命中，缓存读取约 1/10 价

反例：把时间戳、随机 ID 写进 system —— 缓存每轮失效，账单翻十倍
💡 静态层的纪律：能不变的绝不参与变化
STEP 3动态层

缓存命中的边界，画在变化处

前缀缓存按字节匹配 —— 静态在前、动态在后，边界画得对，钱就省得下

缓存前缀 = 静态层 + 已稳定的历史
静态层 · 命中 1/10 价动态层 · 原价
⚡ 缓存边界：历史一旦稳定就并入命中区 —— 每轮只有增量按原价
📜历史消息：旧轮次一旦写完就不再变 —— 天然可入缓存
🔧工具结果：体积大头，回填后也趋于稳定（05 期先瘦身再回填）
⚠️失效陷阱：在历史中间改一个字，其后全部缓存作废 —— 修历史要改就改到尾
这也解释了 12 期的顺序状态机：只追加、不插改，既是协议要求，也是省钱之道
💡 组装顺序不是风格问题 —— 是缓存账单问题
STEP 4预算裁剪

组装的最后一步：算总账

五层拼完先算 token 总量 —— 超过水位线，组装器负责裁到装得下

用量 > 60% 窗口 → 触发裁剪（dev-03 期）
本组装 token 用量水位线 60%
72% —— 超线，触发裁剪
✂️先裁旧工具结果 —— 体积最大、价值最低（dev-03 期三类垃圾）
🗜️再压远期历史 —— 总结成交接单，目标/已做/待办留下
🚫system 永不裁 —— 人设和规则被裁掉，Agent 立刻「失忆变质」
裁剪有优先级：垃圾 → 远历史 → 动态层，静态层和本轮输入最后动
💡 组装器是把关人 —— 模型看到的永远是被裁剪过的世界
STEP 5按需注入

放不下的，给目录就好

大文档不全塞 —— 先给轻量索引，要用哪节再读哪节（just-in-time）

注入索引 → 模型点单 → 工具读取 → 进下一轮上下文
🗂️
给目录，不给全书

注入「资料清单 + 每份一句话简介」—— 实测古诗文 demo：264 页只以索引形态占位（rag-01 期）

🎯
记忆只注相关条目

跨会话记忆按当前任务挑几条（08 期）—— 全量注入是噪声也是成本

🛰️
大活外包给子 Agent

深挖交给干净上下文的子 Agent，只回 1~2k 摘要（09 期）—— 主上下文不沾灰

按需注入的顺序：目录 → 点单 → 读取 → 使用 —— 多一轮工具调用，换来窗口轻装上阵
💡 组装器的终极心法：上下文是预算，不是仓库
