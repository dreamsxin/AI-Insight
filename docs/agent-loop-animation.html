STEP 1接收目标

接收目标

用户给出一句话目标，Agent 把它连同工具说明放进 messages，请求 LLM 开始第一轮思考

messages = [system(工具说明), user(目标)]
🎯 修复 tests/ 目录下失败的单元测试
LLM 读到的上下文⌄
ENV可用工具：bash · read_file · edit_file · grep …… 每个工具附带使用说明
LIMIT只修改代码，不重装依赖 · 修改前先跑测试定位失败原因
💡 目标不会被执行 —— 它只是一段文字，Agent 靠 LLM 把它翻译成一个个具体动作
STEP 2思考规划

思考规划

LLM 读到目标与工具列表，先输出一段思考：拆解步骤、决定第一步

<think> 先跑测试 → 看报错 → 改代码 → 回归 </think>
🧠
LLM · 任务拆解中
1运行测试套件，收集失败用例
2阅读报错堆栈，定位可疑代码
3修改 src/utils/math.ts 的除零分支
4重跑测试，确认全部通过
▸ 下一步输出：调用 bash 工具 →
💡 没有独立的「规划器」—— 计划就是模型的一普通回答，只是格式约定成了清单
STEP 3工具调用

工具调用

模型不直接改文件，而是输出一个结构化的 tool_use，把执行权交还给调用方

{"tool": "bash", "args": {"command": "npx vitest run"}}
assistant 消息 · tool_use
{
  "type": "tool_use",
  "name": "bash",
  "input": { "command": "npx vitest run" }
}
🧠 LLM
tool_use
🤖 Agent
✓ Agent 解析 JSON → 交由真实执行器运行命令
💡 LLM 只「提议」调用，从不亲自执行 —— 执行权在 Agent 代码手里，这是安全边界
STEP 4执行与观察

执行与观察

Agent 跑完命令，把结果作为 tool_result 消息追加进 messages，再次请求 LLM

messages.append({"role": "tool", "content": "2 failed…"})
tool_result · bash
npx vitest run
✗ tests/math.test.ts › divide › by zero
  expected: Infinity  ·  received: NaN
2 failed | 14 passed (1.8s)
🖥 执行器
observation
🧠 LLM 再思考
成功与失败同样宝贵 —— 报错堆栈正是下一轮决策的依据
💡 Agent 的每一步都基于真实世界的反馈，而不是模型想象中的执行结果
STEP 5循环与收敛

循环与收敛

思考 → 调用 → 观察 反复进行，直到模型判断目标达成，输出最终回答

while not done and loops < MAX: think(); act(); observe()
🧠 思考
🔧 发起调用
🖥 真实执行
👁 观察结果
Agent 主循环loop < MAX_LOOPS = 10
🔧 bash → 工具结果
Test Files 1 passed · Tests 18 passed (2.1s) —— 除零分支已修复
💬 最终回答：已修复 src/utils/math.ts:12 的除零分支，18 个测试全部通过
💡 循环次数是预算上限 —— 防止模型陷入「无限重试」的空转
RECAP全景

Agent = LLM + 工具 + 循环

把「一次问答」变成「一串带反馈的迭代」，复杂任务由此完成

目标→思考→工具调用→执行→观察→循环→完成
🧠
模型即大脑

规划、决策、反思都发生在模型侧；Agent 代码只负责搬运消息与执行动作

🔌
工具即手脚

文件、终端、浏览器都封装成工具；接入新工具，Agent 立刻获得新能力

🔄
循环即生命

单次调用是「查询」，带反馈的循环迭代才是「任务」—— 这是 Agent 与聊天机器人的分水岭

“Agent = LLM + 工具 + 循环。”
