STEP 1向量 RAG 答不了的问题

能查一句话，答不了「整体」

向量检索（AI 19 期 / 工坊 02）每次只捞最相似的几个片段 —— 它擅长具体事实，却看不见碎片之间的连线与全貌

✓ 局部问题（擅长）

「退款流程的第三步是什么？」
「X 公司的 CEO 是谁？」

答案集中在一两个 chunk，top-k 一捞就中

✗ 全局问题（抓瞎）

「这批材料总体在讲哪几件事？」
「各方势力之间是什么关系？」

答案散在几十上百份文档里，没有任何一个 chunk 直接写着

朴素 RAG：问题 → 相似片段 → 答案　✗ 没有「把片段连起来」的一步
💡 这正是 AI 19 期「单向量天花板」的升级版：不仅一词多义会丢，跨文档的关系也会丢
STEP 2先让 LLM 读出「谁和谁怎样」

把文档抽成实体与关系

GraphRAG 在建库时多做一道重活：让 LLM 通读每个片段，抽出实体（节点）、关系（边）和关键说法，织成一张知识图谱

① 切文本块TextUnits：文档先切块（工坊 01 的老工序）
② LLM 抽取实体（人/组织/地点）· 关系（收购/任职/投资）· 主张（谁说了什么）
③ 合并入库同一实体跨文档出现 → 合并成同一个节点，边越连越多
💡 向量库存的是「文字碎片」，图谱库存的是「谁、和谁、什么关系」—— 问题可以沿着边走
STEP 3社区发现与分层摘要

给纠缠的节点，分圈子、写总结

用聚类算法（如 Leiden，作用就是自动把连线密集的节点圈成一个个「社区」）分好圈子，再让 LLM 自底向上逐层写摘要，形成一座主题金字塔

全局摘要整库在讲什么
社区摘要每个圈子的主题
实体/关系明细节点与边

🗂️ 类比：给一屋子聊天记录写会议纪要

先分清谁和谁在聊同一话题（社区），每个话题写一段小结（社区摘要），最后把小结汇成总纲 —— 回答「整体如何」时，读摘要金字塔，而不是翻全部原文

💡 这一步是 GraphRAG 的灵魂：答案不再从碎片里现拼，而是提前分层归纳好
STEP 4local 与 global：问法决定走法

查邻居，还是读地图

建好的图谱支持两种提问方式：具体问题沿实体关系走，全局问题让所有社区摘要并行作答再汇总

🔎 Local Search（局部）

先定位问题里的实体，再取它相邻的节点、关系与原文片段，交给模型组织答案

问题 → 命中实体 → 沿图扩展邻域 → 连同原文证据回答
适合：具体的人/事/物之间的关系

🌐 Global Search（全局）

把问题同时发给每个社区摘要（map：各答各的），再把所有回答 reduce 成一份总答案

问题 → map：各社区并行回答 → reduce：排序、去重、综合
适合：「整体趋势/主题/分歧是什么」
💡 这正是 Hermes 09 期「主官+斥候」在知识库上的重演：local 查一个点，global 汇总一群斥候的报告
STEP 5DRIFT 混合检索与成本账

先用地图定方向，再回细节取证

🌐
global 定方向先从社区摘要找到「答案大概在哪个圈子」
🔎
local 取细节再进对应社区沿图取证，补充具体出处
🔀
DRIFT两者合一：宏观不丢、细节有据，可多轮追问
什么时候别上 GraphRAG？　建库时每个 chunk 都要调一次 LLM 做抽取与摘要，索引又贵又慢、还要领域适配
资料 约 20 万 token 以内：直接长上下文塞进模型最划算；只问具体事实：向量 RAG + rerank（AI 19）足够。跨文档的全局主题问题，才是它的主场
✕ 朴素向量 RAG局部事实强，跨文档主题弱
≈ Text-to-SQL结构化数据（数字/表格）交给数据库更准
✓ GraphRAG实体关系密集、需要主题归纳时启用
💡 和工坊 04 的结论一致：先证明简单方案不够，再为复杂性买单
RECAP全景

给知识库画一张关系地图

实体关系抽取 → 社区聚类 → 分层摘要 → local/global/DRIFT 检索

切块→实体/关系→社区摘要→local/global→有据回答
🕸️
从碎片到关系

LLM 把文档抽成实体、关系、主张，同一实体跨文档合并；问题可以沿图的边走，补上向量检索看不见的关联

🗺️
社区摘要回答全局

Leiden 聚类把图分成社区，自底向上写分层摘要；local 查邻域、global 让社区并行作答再 reduce，DRIFT 先定方向再取证

💰
贵在建图，按需启用

每块语料都要 LLM 抽取与摘要，索引成本高；小库直接长上下文、事实问答用向量 RAG，跨文档主题归纳才值得上图谱

图谱回答「这些事之间怎么回事」。”
