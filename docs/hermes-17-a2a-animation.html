多 Agent 的红利是上下文隔离

AI 09 期 / Hermes 09 期的正确姿势：主智能体写计划、子智能体并行探索，每个子代理有干净窗口，只回摘要

✓ 这套设计什么时候成立

子任务边界清晰、彼此独立、产出是可压缩成结论的研究或检查结果 —— 主上下文因此保持干净（65k 原始 → 2.4k 摘要，正是 AI 09 期的账）

独立窗口只回摘要并行省墙钟时间噪声留在子窗口

2025 年的新问题

多 Agent 被当成万能架构：编排、评审、返工都拆成角色互相对话 —— 红利之外的代价开始集中爆发

💡 多 Agent 从来不是「更聪明」的开关，它是一种用隔离换质量、用并行换时间的取舍
STEP 2行业降温：两宗罪

一群智能体，为什么反而更差

2025-06《Don't Build Multi-Agents》引发广泛共鸣：把高度依赖的任务拆给多个代理，两类问题无法回避

① 上下文丢失

子代理只拿到摘要，决策所需的细节在压缩中消失；信息每过一手就薄一层

研究代理看到的用户原话
→ 到规划代理只剩一行结论
→ 关键约束被悄悄丢掉

② 隐式决策冲突

各代理在不可见的地方做了互相矛盾的选择，主代理没有完整轨迹来仲裁

A 选了方案甲、B 按方案乙准备数据
汇总时才发现对不上
返工比单做一遍还贵
行业结论：需要紧密协调、共同决策的工作，线性的单智能体往往做得又快又稳 —— 拆分只在子任务真正独立时才划算
💡 对照避坑 02 期：主智能体必须持有完整决策上下文 —— 子代理可以干脏活，不能替主智能体做取舍
STEP 3被忽略的成本账

并行省下的是墙钟，不是 token

每个子代理各自重发一份上下文、各自跑完整循环 —— 多 Agent 的资源账单可能高出一个数量级

单 Agent ≈1× token
3 个子代理 ≈4.5×
多 Agent 研究 ≈15×（实测）
时间账与金钱账要分开看：并行让墙钟更短，但总 token 随代理数成倍上涨 —— 简单任务上，这笔钱买不到正确率
💡 和 16 期的思考预算同理：多出来的计算要花在真正独立、信息超窗的子任务上
STEP 4那什么时候还该拆

三个成立条件

多 Agent 仍被一线团队保留，但适用面比 2024 年的狂热叙事窄得多

🔭

多方向同时搜网页/文档，结果天然可并列汇总

💾

每份材料数万 token，读完只回结论，保护主窗口

🧱
边界清晰

子任务输入输出明确、互不依赖、可独立验收

90.2%
多智能体研究系统在难题上的相对胜率
（代价是 ≈15× token）

不让子代理无限自我繁殖
💡 新共识一句话：单 Agent + 子代理（窄用）是默认形态，多 Agent 编排只在证据充分时才上
STEP 5当代理分属不同组织

A2A：代理之间的横向协议

MCP 解决「Agent ↔ 工具」的纵向接入；Google 2025-04 提出的 A2A 解决「Agent ↔ Agent」的横向协作，后移交 Linux 基金会

🔌 MCP（纵向）

Agent 连工具/数据：tools、resources、prompts —— 不窥探对方内部状态，「作为工具被调用」

🤝 A2A（横向）

两个自治 Agent 对等协商任务：能力发现、委派工作、交接产出，各自保留内部黑盒

Agent Card · .well-known/agent.json Task 长任务 Message 消息 Artifact 产出物 SSE / 异步推送
名片式发现（Agent Card 声明能力）与 H16 的 MCP Tasks 状态机呼应：跨组织协作仍走任务句柄，不共享大脑
💡 协议只提供「礼貌交接」的信封 —— 决定要不要拆、拆给谁的，仍是架构师
RECAP全景

从多智能体狂热，回到单智能体默认

隔离是真红利，冲突是真代价；窄用子代理，横向交给 A2A 协议

单 Agent 默认→子代理隔离探索→只回摘要→A2A 跨组织
🧠
默认一个主智能体

高度依赖的任务线性做更稳：避免上下文丢失与隐式决策冲突；主智能体必须持有完整决策轨迹，子代理只干边界清晰的脏活

💰
并行省墙钟，不省 token

多 Agent 总账单可达约 15 倍；只为广度研究、信息超窗、可独立验收的子任务买单，连续失败即收敛回主线
