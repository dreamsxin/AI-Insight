STEP 1账单先撞线

messages 只进不出，迟早撑满

主循环每转一轮，messages 就长一截，而且下一轮要把全部历史原样重发（hermes-04 期）—— 上下文窗口是有硬边的

第 N 轮输入 token ≈ 全部历史之和（dev-02 期的成本公式）
system你是出行助手……420
user我是杭州人12
assistant好的，已了解……18
user帮我查明天的天气15
tool{ weather: "晴转多云…" }210
assistant明天杭州晴转多云……46
user那周末呢？顺便推荐个徒步路线31
上下文占用97% · 128k 窗口告急 水位线
💡 不压缩只有两个结局：超窗报错，或者账单爆表
STEP 2最省事的做法最危险

裸截断：删掉最早的消息

超了就从头删 —— 实现只要一行，可最早的消息里，往往住着最基础的事实

system你是出行助手……删？
user我是杭州人　← 关键事实删！
user帮我查明天的天气
tool{ weather: … }
user周末去哪徒步？保留
✕ 截掉头部 N 条 —— system 也可能一起遭殃，模型连人设都丢了
⚠️ 下一轮模型答：「请问您在哪个城市？」 —— 它不是变笨了，是那条事实已经从它的世界里消失了；用户体验：「我不是说过了吗？」
💡 截断删的不是「旧消息」—— 是模型世界观的地基
STEP 3滑动窗口

一扇滑动的窗：钉住头顶，保住尾巴

标准做法：system 永远钉在最前，只保留最近 N 轮 —— 窗口随对话向右滑动，旧消息滑出、新消息滑入

messages = [system] + history.slice(-N)
📌 system 钉死更早的轮次 → 滑出窗口最近 N 条 →
system你是出行助手……（永不滑出）📌
user我是杭州人出窗
user明天天气？出窗
tool{ weather: … }出窗
user周末徒步路线？窗内
assistant推荐九溪烟树……窗内
user那附近有素斋吗？新滑入
比裸截断安全：人设与规矩永不丢，最近的语境完整 —— 但出窗的事实仍然会忘，所以它常和下一招配合使用；需要长期记住的事实交给记忆系统（pat-03 期）
💡 窗口策略的底线：头顶的 system 不能滑走，眼前的对话不能切断
STEP 4滑出之前，先榨干

摘要压缩：旧消息滚成一张便签

出窗的消息不是直接扔 —— 先用一次模型调用把它们压成摘要，后续只带便签，不带原文（ai-07、hermes-02 期都演过这一招）

旧 messages → summarize() → 一条 system/assistant 摘要
📜 出窗原文（第 1–12 轮）
→
📝 摘要便签
用户在杭州，周末偏好轻徒步；已推荐九溪；不吃辣；预算人均 200 内。
5.8k token 原文 ⟶ 1.6k token 摘要 · 关键事实都在
🧠 压的是措辞，留的是事实：数字、决定、未完成事项必须进摘要 —— 摘要 prompt 里点名要求
🔁 可以递归滚雪球：旧摘要 + 新出窗消息 → 新摘要，永远只有一张便签（compaction，dev-03 期）
💡 窗口负责保眼前，摘要负责留住过去的骨架
STEP 5生产环境长什么样

三招不是三选一，是夹成三明治

真实 Agent 的每一轮输入，是分层拼出来再按预算裁剪的（hermes-13 的五层组装 + 水位线）

📌 system：人设 + 规矩 + 工具说明永不裁剪
📝 历史摘要便签（滚动压缩）5.8k→1.6k
🪟 滑动窗口：最近 N 轮原文完整保留
💬 本轮新消息 + 按需检索的记忆刚滑入
system 摘要 窗口 留给生成的预算
裁剪也有顺序：先丢可重新检索的外部资料 → 再压更早的对话 → system 与未完成任务最后才动；长期事实不靠摘要硬扛，走外置记忆库按需召回（pat-03 期），这正是 dev-03 说的「外置」
💡 好的上下文管理 = 头顶钉死、中间压缩、尾巴完整、长期外置
RECAP全景

窗口有限，遗忘要讲策略

撞线 → 拒绝裸截断 → 滑窗保尾巴 → 摘要留骨架 → 分层拼预算

📈 token 撞线→✕ 不裸删→🪟 滑动窗口→📝 摘要压缩→🧱 分层+预算
🪟
窗口是底线方案

system 钉死、最近 N 轮完整；实现简单、延迟为零，代价是出窗即忘

📝
摘要留住事实骨架

5.8k→1.6k，数字与决定必须保留；摘要可递归滚动，始终一张便签

🧱
实战是分层组合

system + 摘要 + 窗口 + 本轮，按 token 预算有序裁剪；跨会话的事实外置到记忆库

“头顶钉死，中间压缩，
尾巴完整，长期外置。”
