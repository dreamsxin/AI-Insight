01拆开看

普通 MoE 的一生

token 要去专家所在的卡上算，所以得先寄过去，算完再收回来。

三段式3 次 kernel
dispatch 专家 GEMM combine
每段结束，中间结果都写回显存；下一段再从显存读回来。

这三段里，只有中间那段在算；前后两段本质是「搬」。

一次 decode 要走过几十层，这一来一回就重复几十次。
02账

来回几趟？

激活值本身不大，但它的读写次数和层数一样多。

三段式6 趟
Mega MoE1 趟

每层「写 + 读」各算一趟：三段式 3 写 3 读 = 6 趟；融合后只在最后写一次结果。

省的不是漂亮，是每层每步都要付一次的显存往返。
03融合

一个 persistent kernel 干完三段

token 块留在片上，专家的权重流过去，而不是 token 流过去。

Mega MoE1 次启动
发 专家 GEMM 收
三段在同一个 kernel 里接力，中间结果不出 shared memory。

代价是：这个 kernel 必须自己管好「按哪个 BLOCK_M 切 token、scale 放在哪、通信什么时候插进来」。

它不是一个更快的算子，而是一个把三段编进同一份代码的调度器。
04尺子

scale 也在片上就地生成

4 位权重要用，就得有尺子；尺子不能等落盘之后再算。

省掉的不只是显存往返，还有一次独立的「把激活量化一遍」的 kernel。
05布局

尺子得按 GEMM 的形状重排

这里藏着最容易踩的坑：数据对，但位置不对，TMA 就搬错。

要素为什么这么定
BLOCK_M由 GEMM 反推出来的 token 分块大小，scale 按它分块填充
128×4 转置块内行号要重排，否则 TMA 读到的尺子和数据错位
padding 到 128不足一块的要补齐，补出来的行保持原值，不能乱写
融合带来的复杂度，几乎全在这种「布局对齐」上，而不是数学上。
06通信

算和发，用同一批 SM

既然三段在同一个 kernel 里，通信就不能再「等算完」。

混合调度
一部分 SM 专管收发

通信线程和计算线程同时在场，token 一边到一边算。

可调
用多少 SM 做通信

按 EP 规模与 top-k 推一个理论值，再留出计算要用的部分。

前提
只在 scale-up 域内成立

跨机之后带宽掉一个量级，融合的收益会被通信吃掉。

所以官方口径是「scale-up 域内的通用解」—— 域外的 MoE 还得另想。
