AGENT 模式进阶 · 07

接力，不是合唱

多 Agent 不该同时开口——
该像接力赛：一棒跑完，交接，下一棒

向下滚动 · 先回忆一下"合唱"为什么难听↓
01 · 合唱的问题

一群智能体同时开口，往往更差

hermes-17 的结论在这里依然成立——
所以先弄清楚它错在哪，才知道分工什么时候对。

🗣️
互相说服，误差不降反升

没有共同事实基线，每个 Agent 都在为自己的版本辩论——token 花了，结论更乱了。

🔁
责任稀释

"大家"决定 = 没人决定。出错时无法定位是哪一环引入的。

🎭
省的是墙钟，费的是 token

并行的收益只在互不依赖的任务上；互相依赖的活并行，只是在制造协调成本。

那多 Agent 就没用了？不是——换一种组织方式：不许同时开口
合唱的病根是"同时"和"互相"。接力把这两样都拿掉了。
02 · 六棒接力

每一棒三样东西

点任意一棒，看它的输入、输出与验收标准。
窄职责 = 只对这三样负责。

→ → → → →
每棒都是窄 Agent 或纯函数——不做上一棒的事，不做下一棒的事
参考实现：examples/compliance-flow-demo/ 的四个脚本即前四棒的规则版（零 LLM 依赖）。
03 · 阶段墙

接棒点不是自动流转，是人工确认

黄点不是装饰——是墙。
上一棒的产出先过验收，人签字，下一棒才开始。

资料收集产出：案件档案
⛔用户确认
材料规划产出：本轮清单
⛔用户确认
文稿生成产出：草稿
⛔用户编辑定稿
确认点把流水线切成段：错误最多传播一段，且每段留下一次人工签字的审计痕迹
关键闸门（事实核对、必需材料、提交安全门槛）只能由人打开——Agent 无权放行
这也是审计的来源：每个确认点 = 一条"谁在什么时候放行了什么"的记录。
04 · 对照

单 Agent 主循环 vs 流水线

不是谁取代谁——是两种组织方式，各有地盘。

单 Agent 主循环（HERMES ·04）
  • think → act → observe 一圈圈转
  • 适合：探索性任务，路径未知
  • 灵活，但路径与质量都靠模型自觉
  • 一个上下文，一处失守全线失守
    • 流水线接力（本集）
  • 固定棒次，每棒窄职责
  • 适合：流程已知、错误不可逆的对外任务
  • 质量靠结构：验收标准 + 确认点
  • 错误被墙隔断，可定位可回滚
    • 经验法则：流程能画成一张确定的图 → 流水线；画不出来 → 主循环
    两者也能嵌套：某一棒内部就是一个主循环 Agent——比如"资料"棒自己跑工具循环去收集。
    05 · 成立条件

    分工什么时候是对的

    三个条件同时满足才上流水线——
    缺任何一个，退回单 Agent 主循环。

    1
    错误不可逆

    产出会离开系统（对外提交、正式文稿）。发错了收不回来，值得为它加墙。

    2
    每段有独立验收标准

    能写出"这棒合格长什么样"。写不出验收标准的段，拆了也是白拆。

    3
    确认点隔得开

    棒与棒之间等得起人工确认。实时对话式的任务等不起，硬拆只会添堵。

    缺一即退回：一个守好护栏的主循环 Agent，胜过一条没有闸门的流水线
    反面教材就是第 01 屏的合唱：三条件一个都不满足，只是把成本翻了几倍。
    06 · 收束

    一屏记住

    接力式流水线
    窄职责 × 验收标准 × 人工确认点

    把多 Agent 从"一群同时开口的合唱团"变成"一支各司其职的接力队"：每棒只对输入/输出/验收负责；接棒前有人签字；错误最多传播一段。成立条件三条——错误不可逆、每段可验收、等得起确认——缺一，就退回单 Agent 主循环。
