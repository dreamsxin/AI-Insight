推理原理 · 06

别让 GPU
等 CPU

最贵的浪费不是算错，
是这条流水线上规律出现的空格。

GPU 干活灰色：在等 CPU 发下一条命令
向下滚动↓
01一步

每生成一个字，其实是四件事

两件在 CPU 上，两件在 GPU 上，交替进行。

1
排下一批CPU
2
跑前向GPU
3
采样GPU
4
收尾处理CPU
第 4 步要拿到第 3 步的结果，必须同步一次
问题就在这次同步：GPU 交完结果就闲着，等 CPU 排下一批。
02缝隙

同步之后，显存空转

红色斜纹就是这个空洞：GPU 有活可干，却在等人。

GPU
前向
采样
空转
前向
采样
CPU
排批
等待
收尾
排下批

空闲时间不算长，但每个 decode step 都会出现一次。
几百步叠起来，就是白白烧掉的卡时。

这不是代码写得慢，而是流水线的结构性空档。
03缝合

把 CPU 的活，挪到 GPU 忙的时候

GPU 跑第 N 步时，CPU 已经在准备第 N+1 步。

GPU
前向 N
采样 N
前向 N+1
采样 N+1
前向 N+2
CPU
排批 N+1
收尾 N−1
排批 N+2
收尾 N
排批 N+3

两条泳道错位咬合，GPU 再也没有空隙。
这就是常说的零开销批调度。

代价是：调度器要处理"还没拿到的结果"，逻辑复杂度上去了。
04切片

长 prompt 不能一口气霸占 GPU

切成小片，和正在解码的请求混在一起跑。

整段
一整段 prefill：别人的 decode 全停
切片
片 1
decode
片 2
decode
片 3

chunked prefill 把"一次长阻塞"换成多次短插入。
TBT 的抖动被压平了。

但切多大？太小浪费启动开销，太大又把别人堵住 —— 需要算。
05预算

这一步到底能塞多少 token

给一个时间预算，用成本曲线反解出片大小。

曲线：cost(q, c) 随 token 数平方增长 交点：这一片的最优解
预算单位是纳秒，上限 32768 token；组内再取一次最小值，避免有人超时。
06批处理

有人上车，有人下车，车不停

不是等一整批跑完再换人，而是每一步都能换。

第 1 步第 8 步第 16 步
队列里的空位立刻被新请求填上 —— 吞吐来自"位子不空着"，而不是"算得更快"。
07小结

排班排满了，显存却堆满了

调度解决了"谁来算"，接下来是"算过的东西放哪"。
