STEP 1单 Agent 困境

单 Agent 困境

让一个 Agent 独自调研竞品 —— 它会把上下文亲手塞满

读 30 个网页 ≈ 数万 token 全进同一个窗口
刚接任务8k tok · 状态好
读完 15 页48k tok · 开始吃力
读完 30 页爆满 · 分析质量下降
✗ 亲手塞满自己的上下文 = 自己把自己变笨
💡 探索的「脏数据」全堆在同一个窗口里 —— 这是单 Agent 的天花板
STEP 2拆任务

拆任务

主 Agent 只写高层计划、分派三路 —— 自己不亲自下场翻网页

plan → spawn(worker, subtask) ×3
1调研三家产品的价格方案→ 🛰️ 子 A
2对比核心功能清单→ 🛰️ 子 B
3收集真实用户口碑→ 🛰️ 子 C
主官只画地图 —— 不亲自探路
💡 主 Agent 专注拆解与综合—— 体力活交出去
STEP 3子 Agent 开工

子 Agent 开工

三个子 Agent 各领一个干净的上下文窗口，放手深挖

每个 worker = 独立窗口 · 互不可见 · 可并行
🛰️子 A · 价格12 个网页
22k tok 消耗
🛰️子 B · 功能9 个页面
18k tok 消耗
🛰️子 C · 口碑15 条评论
25k tok 消耗
上下文隔离 —— 脏活累活全部留在各自的窗口里，主帐不被污染
💡 每个斥候都有自己的「一屏」—— 深挖几万 token 也不影响主官
STEP 4只回传摘要

只回传摘要

子 Agent 探索完，只把浓缩结论交回 —— 万 token 进，千字出

worker → summary(800–900 字) → 主 Agent
🛰️ 子 A22,000 tok 探索→800 字价格摘要
🛰️ 子 B18,000 tok 探索→700 字功能对比
🛰️ 子 C25,000 tok 探索→900 字口碑要点
65k token 的原始工作量 —— 主上下文只收到 2.4k
💡 大量消耗留在子窗口里—— 主上下文只收结论
STEP 5汇总

汇总

主 Agent 的窗口依然轻量 —— 综合三份摘要，产出最终报告

synthesize(3 × summary) → final report
🧑‍✈️ 主窗口仅 +2.4k tok 思路始终清晰 三份报告可溯源
竞品分析报告：X 产品定价激进但功能少；Y 功能全但口碑一般；建议主打性价比+服务差异点……
来源 A · 价格来源 B · 功能来源 C · 口碑
探索与决策分离 —— 这就是关注点分离在 Agent 架构上的落法
💡 主官轻装上阵 —— 斥候的辛苦，只以上报的形式存在
RECAP全景

上下文隔离 = 关注点分离

拆任务 → 并行探索 → 只回摘要 → 汇总

拆任务→并行探索→只回摘要→汇总

隔离即分工

三路同时开工 —— 墙钟时间约等于最慢那一路
