STEP 1工具调用发起

工具调用发起

LLM 决定打开页面，输出 tool_use；MCP Client 不解释它，只按协议原样转发给 MCP Server

tools/call { name: "navigate_page", arguments: { url } }
🧠 LLM
tool_use
🔌 MCP Client
转发
⚙️ MCP Server
tool_use · assistant 消息
{
  "name": "navigate_page",
  "arguments": { "url": "https://example.com" }
}
Client 是「邮差」—— 内容与格式对它透明，只负责传递
💡 协议统一后，Server 换成数据库、Git 还是浏览器 —— 模型侧零改动
STEP 2协议翻译

协议翻译

MCP Server 把面向模型的工具名，翻译成 Chrome 听得懂的 CDP 命令

mapping: tool_name → CDP domain.method
MCPnavigate_page→Page.navigateCDP
MCPtake_screenshot→Page.captureScreenshotCDP
MCPevaluate_script→Runtime.evaluateCDP
MCPclick→Input.dispatchMouseEventCDP
工具是给模型看的名片，CDP 才是浏览器的「方言」
💡 这层「翻译」让 LLM 只需认识十几个工具 —— 而不是 CDP 的几百个方法
STEP 3WebSocket 下发

WebSocket 下发

Server 通过 DevTools 的 WebSocket 长连接，把 CDP 命令发给真实运行的 Chrome

ws://127.0.0.1:9222/devtools/page/<id>
⚙️
MCP Server
CDP CLIENT
Page.navigate
🖥️
Chrome
DEVTOOLS :9222
WebSocket 帧 · 发送 →
{"id": 42, "method": "Page.navigate", "params": { "url": "https://example.com" }}
CDP 不是 HTTP —— 命令与事件都走同一条 WebSocket 长连接
💡 长连接的意义：命令可下发、事件可推送 —— 这是自动化「实时感」的来源
STEP 4执行与事件回传

执行与事件回传

浏览器执行命令后，先回 ack 响应，再持续推送页面生命周期事件

← {"id":42, result}  ← event Page.loadEventFired
🖥️ Chrome
ack + events
⚙️ MCP Server
WebSocket 帧 · ← 接收
← {"id": 42, "result": {"frameId": "…"}} ✓ ack
← {"method": "Page.frameStartedLoading"}
← {"method": "Page.loadEventFired"} ✓ 页面就绪
事件是浏览器的「心跳」—— 监听它们才知道页面真的加载完了
💡 靠事件而非固定延时 —— 自动化才能做到「加载完就执行下一步」
STEP 5结果转为工具消息

结果转为工具消息

Server 把 CDP 结果包装成 tool_result 沿原路返回，追加进 messages，LLM 决定下一步

messages.append({"role": "tool", "content": …})
🖥️ Chrome
CDP 结果
⚙️ MCP Server
tool_result
🧠 LLM
🔧 navigate_page → 工具结果
已打开 https://example.com · 页面标题 "Example Domain" · 加载耗时 312ms
💬 LLM 决策：页面已就绪 → 继续调用 take_snapshot 抓取页面结构
💡 一次「打开网页」= 一圈完整链路 —— 每个工具调用都是这样的一来一回
STEP 6快照交付

快照交付

MCP 工具不只「转发」—— 它把 CDP 海量原始数据，精炼成模型读得动的结构快照

take_snapshot ← DOMSnapshot.captureSnapshot()
CDP 原始返回 · DOMSnapshot.captureSnapshot
{"documents":[{"strings":["#text","div","class",…
"layout":[{"nodeIndex":0,"styles":[…],"bounds":[…]},
…"textBoxes":[{"start":0,"length":8,… ▌ 后面还有数十万行
⚠ 约 8.2 MB 原始布局数据 —— 直接塞进上下文，模型「读不动」
MCP Server 精炼 · 只留角色 / 名称 / 引用⌄
take_snapshot → 工具结果 · a11y 树
- document Example Domain
- heading "Example Domain" [level=1]
- paragraph "This domain is for use in illustrative…"
- link "More information…" ref=s1e5
✓ ≈ 1.2k tokens · 模型一屏读完 · ref 可直接定位点击
💡 这就是 MCP 工具封装的价值：脏活累活在 Server 侧做完，模型只收到决策需要的干净结构
RECAP全景

端到端链路

模型说「工具」的语言，浏览器说 CDP 的语言，MCP Server 负责中间的翻译

tool_use→MCP 转发→协议翻译→WebSocket→Chrome 执行→事件回传→tool_result
🧩
双向解耦

模型只认工具，浏览器只讲 CDP；中间的 MCP Server 让两端互不感知、各自演进

🎁
能力即封装

截图、点击、抓快照…… 每个 CDP 能力都能包装成一个对模型友好的工具

🧪
真实即反馈

自动化跑在真实浏览器里 —— 渲染、JS 执行、网络请求全是真实结果，不是模拟

“模型说工具的语言，
浏览器说 CDP 的语言，MCP 负责翻译。”
