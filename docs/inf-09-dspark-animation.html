05收益

并发越高，省得越多

因为省下来的验证算力，可以立刻拿去服务别的请求。

06反例

16 并发时，它反而更慢

因为这时候算力本来就是富余的。

📉
−1.5%

低并发下，少验几个并不能换来更多吞吐，反而增加了调度开销。

📈
+11%

96 并发时，省下的验证算力严重稀缺，每一份都变成了吞吐。

任何"自适应"的优化，都有它不该开的区间。
07耦合

它和异步调度还打架

排第 N+1 步时，第 N 步的置信度还没回到 CPU。

🧠
CPU 只定总预算

既然拿不到每个请求的分数，就不在 CPU 上决定长度。

⚙️
长度在 GPU 上现算

累积乘积 → 全局排序取 top-k → 融合重映射写回固定内存。

🔁
调度器不再"全知"

它从"知道每个请求要多少"退化成"给一个总盘子"。

这是零开销调度带来的连锁设计债：省下的是时间，付出的是调度器的确定性。
08小结

猜得快，还得保证写对

下一集换个方向：不再省计算，而是省"浪费的计算"。

🎯
接受率会衰减

固定验证长度对后排 token 是浪费。

📊
按收益裁剪

置信度打分 + 排序，选出边际收益最高的前缀。

⚖️
收益看并发

低并发会亏，高并发能到两位数百分比。
