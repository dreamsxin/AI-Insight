STEP 1三种不听话

症状在模型侧，病根在工具侧

上手最常撞的三堵墙 —— 先对号入座，再回头查你写的工具定义

别急着换模型 —— 先查工具说明书
🎯
选错工具

叫它读本地文件，它偏偏去联网搜索 —— 因为 fetch_data 的描述里没说清「仅用于外网」

🎭
参数幻觉

日期栏填「昨天」、用户 ID 凭空编 —— 因为参数定义里没写格式、没给枚举，它只能自由发挥

🌀
选择过载

一口气挂 30 个工具，它挑花眼 —— 该调的不调、不该调的乱调

MAST 研究测了 1600+ 条真实 Agent 轨迹：任务失败率 41%~87%，幻觉参数、无效重试都是高频项 —— 工具定义就是模型看世界的窗口，窗户糊了，别怪屋里人乱走
💡 大多数「模型不听话」，病根都在工具侧 —— 逐条可修
STEP 2命名与描述

描述是写给模型的 prompt

同一个工具，两种写法 —— 模型的表现天差地别

命名即文档 · 描述写「何时用 + 何时不用」
✕ 这样写
name: do_stuff
description: "执行相关操作"   ← 模型只能靠猜
✓ 这样写
name: search_orders
description: "按客户 ID 查询订单列表。
仅用于查询历史订单；创建订单请用 create_order。
status 必须取枚举值，不要自行发挥。"
🏷️ 名字即文档 📐 一个工具一件事 🚧 写清边界与反例
💡 你写的是文档，模型读到的是全部事实 —— 没写的它就编
STEP 3参数 schema

能枚举就枚举

每少一个自由文本字段，就少一类幻觉 —— 把「猜」的空间收干净

type + required + enum + default
🎚️
枚举代替自由文本

status: ["open","shipped","closed"] —— 三选一，不用猜拼写

📅
格式写死在描述里

日期统一 ISO 8601（2026-01-01），别让它发挥「下周三那天」

🛡️
严格模式兜底

开 strict / JSON Schema 校验 —— 传错直接拒，错误信息里写清该传什么

schema 校验不是不信任模型 —— 是把澄清错误的时间从「一轮对话」缩短到「一次 400」
💡 参数定义越窄，模型发挥越稳 —— 自由度是幻觉的温床
STEP 4数量与分组

别把整间库房倒给它

工具越多选择越难 —— 按任务打包，而不是一次全挂

按需注入 · 分层路由：先选工具组，再选组内工具
✕ 一次全挂 20 个
read_fileweb_searchsend_mailrun_sqldeployweibo_postcalcimg_genpaycron…
✓ 本任务只挂 5 个
read_fileedit_filerun_testsgit_diffbash
写代码的任务别挂发微博 —— 无关工具是干扰项，每多一个，选错的概率就涨一点
工具真多到砍不动：先让模型选「工具组」，再进组里挑具体工具
💡 工具箱按任务打包 —— 菜单越短，点对率越高
STEP 5返回值友好

返回值是模型的眼睛

它只能看见你给它看的 —— 返回什么，决定它下一步怎么走

可行动的错误 · 截断与分页 · 结构稳定
✕裸抛错误 —— 它只能再瞎试
Error: ENOENT
✓可行动的错误 —— 看一眼就能自救
文件 config.json 不存在。 目录下相似文件：config.yml、config.old 建议：确认扩展名后重试。
大结果要截断加分页 —— Claude Code 默认把单次工具响应截在 25,000 token；51 万字符网页塞回来，烧钱又淹重点（Hermes 05 期 / 错误自愈见 11 期）
💡 错误信息写得越可行动，Agent 自愈的成功率越高
RECAP全景

把工具当产品做

症状归因 → 命名描述 → 参数枚举 → 数量分组 → 返回友好

症状在模型侧→病根在工具侧→命名+描述→参数收窄→返回可行动
📖
描述即 prompt

何时用、何时不用、边界反例 —— 写给模型的说明书，一个字都算数

🎚️
收窄自由度

枚举、格式、strict 校验 —— 每少一个自由字段，少一类幻觉

🎚️
菜单越短越准

按任务注入工具、分层路由 —— 别让模型在 30 个选项里猜谜
