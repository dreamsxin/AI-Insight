# Agent 工程模式：高风险对外生成任务的闸门设计 · 资料汇编

> 调研时间：2026-11-04 · 场景：Agent 产出会离开系统的合规/审批类工作流（对外提交、正式文稿、报告递交）
> 一句话结论：**当生成物的错误不可逆时，"生成"只是流水线的一棒——真正保证质量的是棒与棒之间的状态机与闸门。** 提示词里写"请不要编造"约束不住 anything；下面八个模式把约束搬进数据结构和流程控制。

---

## 一、问题：为什么提示词约束不够

生成物一旦对外（提交给平台、发给客户、进入审计），错误不可逆，幻觉的代价从"答错了"变成"替用户做了承诺"。这类场景下光靠系统提示词有四个失效点：

1. 模型会顺着输入的措辞**自行补全结论**（通知里写了 X，模型默认用户认可 X）；
2. "不知道"没有合法出口——占位内容被流畅的句子覆盖；
3. 约束没有**状态**：材料齐不齐、事实核没核，提示词记不住；
4. 约束没有**权限**：谁能绕过检查、什么算例外，没有仲裁。

解法是把每一类约束落成一种数据结构：状态机、闸门、分级、计数、快照。以下八个模式按"分工 → 事实 → 证据 → 护栏 → 失败"的顺序展开。

---

## 二、八个模式

### M1 · 流水线分工 + 人工确认点

**问题**：一个全能 Agent 端到端做完收集、判断、写稿、提交，出错时无法定位，也没有人工介入点。

**做法**：按职责拆成窄 Agent（如 分流 → 资料 → 规划 → 写稿 → 质检 → 提交），**棒与棒之间放人工确认点**。每棒声明三样东西：输入、输出、验收标准。

**成立条件**（呼应 hermes-17 "一群智能体反而更差"）：错误不可逆 × 每段有独立验收标准 × 确认点隔开。三者缺一，不如回到单 Agent 主循环。

**现有铺垫**：hermes-17 A2A 多 Agent 反思、pat-01 Plan-and-Execute、hermes-20 从零造 Harness（三道保险丝）。

### M2 · 正交维度，不是互斥路线

**问题**：把场景硬编码成 A/B/C/D 互斥路线，组合态（"涉及关联 + 上轮被拒 + 部分事实争议 + 文本与附件"）无处安放，最后要么乱塞、要么丢信息。

**做法**：拆成正交字段（问题类型 / 阶段 / 立场 / 提交形式各自独立、可多选），标签只作分流提示，**不替用户做定性**。旧路线编码仅作历史兼容。

**工程要点**：数据模型、界面文案、提示词三层对同一组字段保持同一语义；"标签"与"结论"之间隔一个人工确认。

### M3 · 事实状态机：不知道就说不知道

**问题**：模型把"待核"写成了"已确认"，且没有任何机制拦住它。

**做法**：给事实一个显式状态机——**待核 → 已核（对照来源）→ 来源冲突（暂停对外生成）**。配套三条硬规则：
- 占位符保留到人工核实后清零，**未提供的事实不得自动补全**；
- 来源之间冲突即暂停对外文稿，记录冲突字段与来源后转人工；
- 输入一变（新增材料、改字段），已生成的草稿**即失效**，需按当前资料重生成。

**口诀**："暂未发现冲突"不等于"确认属实"。

**现有铺垫**：dev-03 上下文工程、hermes-20 三道保险丝、dev-04 评估观测。

### M4 · 证据链是一等公民

**问题**：材料清单上"已上传"的文件被当成"已证明"的事实；文件名 ≠ 证据。

**做法**：一条证据链 = **主张 → 材料 → 材料中可核的内容 → 来源 → 支持范围**。断在任何一环都不构成证据。工程化三件套：
- 每份材料**双字段**：内容说明 + 它支持的事实/论点（只填文件名不合格）；
- 对外正文中**自动生成连续编号的引用清单**，顺序与正文引用、附件顺序一致；
- 链有缺口即**阻塞**对外生成，而不是给个提醒。

这本质是一条图路径：主张与材料是节点、"支持"是边——与 rag-kg-ontology-research 的本体视角完全同构（必需 vs 建议就是本体里的两类属性，见 M5）。

**现有铺垫**：rag-03 拒答与强制引用、rag-05 GraphRAG。

### M5 · 必需 vs 建议：两种来源两种待遇

**问题**：系统生成的材料建议被当成硬性要求，反之亦然——用户被误导。

**做法**：材料来源分两类并**分开展示**：
- **明确要求**：能在原始通知/规则原文中定位到依据的——保存原文摘录；关键词命中但找不到原文依据时只能标"待核提示"；
- **模式建议**：系统按场景推演出的建议——用户决定是否纳入，纳入后才进入本轮提交包，未纳入只显示风险、不阻塞。

**工程要点**：必需项不可标记"本轮不处理"；历史上有过"不处理"记录的必需项，总检仍然拦截。

### M6 · 检索样本的可信分级

**问题**：参考案例（RAG 检索结果）被直接当成"成功先例"写进新方案。

**做法**：检索结果分级——只有能**回指平台书面结果**或经审核确认的样本才可标"已验证"；撤回、口头确认、结果未知的一律降级，不得用作成功依据。**找不到合格样本时必须显式记录**（检索范围/日期/原因），把"结论的哪部分属于推断"写清楚——不得虚构样本编号、成功结果或通过率。

**现有铺垫**：inf-25/26/27（评测口径与判分可信度）、dev-04 评估观测。

### M7 · 护栏四态与独立总检

**问题**：检查项只有"通过/不通过"两态，要么全堵死、要么被人情绕过。

**做法**：检查项四态——**阻塞**（条件未满足）/ **提醒**（有风险，人工判断）/ **不适用**（与本案无关，须填理由）/ **本轮不处理**（用户决策，须填原因并留档，可恢复）。配套三条：
- 阶段化清单：未进入的阶段不显示其检查项（只减少噪音，不放宽门槛）；
- **同类门槛不可用例外状态解除**（关键事实、必需材料、安全门槛不得标"不适用"绕过）；
- 提交安全门槛由**总检独立校验**——隐藏、删除或标记不处理都不放行；阶段检查不提供删除选项，保住审计链。

**现有铺垫**：pat-06 软硬护栏（那集讲哪层软哪层硬，这里讲门有哪些等级、谁有权开）、hermes-14 Hooks。

### M8 · 重复失败升级与 append-only 快照

**问题**：同样的输出被反复提交、反复被拒，Agent 在原地打转。

**做法**：
- **计数升级**：同类拒绝第 2 次要求记录"本轮新增信息/变化维度"（逼差异显式化），第 3 次停止原入口重试，转入升级评估——不是重试，是换问题问。这就是 `guards.py` repeat detection 的领域版；
- **快照 append-only**：每轮提交的正文、附件清单、审核意见作为独立快照归档，退回开新轮**不覆盖**旧轮；已完结档案只读。

**现有铺垫**：hermes-18 checkpoint（日志倒带）、`store.py` 会话检查点、inf-23 确定性。

## 三、动画选题（按系列归属）

### P0 · dev-06《证据链》——把"有文件"和"能证明"分开

- **一句话**：一条链 = 主张 → 材料 → 可核内容 → 来源 → 支持范围；断在任何一环都不构成证据。
- **分镜草案（7 屏）**：① 封面：一摞文件 vs 一条链；② 只有文件名为什么不算（"已上传"≠"已证明"）；③ 五环链展开逐环点亮；④ 双字段：内容说明 + 支持的事实/论点；⑤ 必需 vs 建议——本体的两类属性（M5）；⑥ 缺链即阻塞：正文自动编号引用与附件顺序一致；⑦ 收口：引用不是装饰，是链路——呼应 rag-03。
- **衔接**：rag-kg-ontology-research 第六节预埋了这个选题；rag-demo 的古诗文语料可直接当屏上演示数据（"'静夜思'是李白写的"这条主张，链条上每环是什么）。

### P1 · dev-07《不知道就说不知道》——事实状态机（M3）

- **分镜草案（6-7 屏）**：三态流转图；来源冲突即暂停；占位符为什么不能自动补；生成物失效条件；"暂未发现冲突 ≠ 确认属实"。

### P1 · pat-07《接力，不是合唱》——流水线型多 Agent（M1）

## 四、demo 选题：`examples/compliance-flow-demo/`

对照 `examples/agent-harness-demo/`（01–09 已成型）的体例，新建一个**零 LLM 依赖、pytest 可测**的工作流演示包——八个模式全部可以规则化，正好展示"高风险流程控制不是大模型的专利"：

```
examples/compliance-flow-demo/
├── README.md            # 与八个模式一一对应的导览表
├── _common.py           # FakeLLM（规则式）、案件/任务状态 dataclass、正交维度字段
├── 01_triage.py         # M1+M2 分流：维度收集与追问；证据不足 → "待识别"不硬猜
├── 02_evidence_gate.py  # M4+M5 证据链缺口矩阵：必需 vs 建议，缺链即阻塞
├── 03_position_draft.py # M3 立场分支文稿：立场决定结构；事实未核不生成对外稿
├── 04_rejection_loop.py # M7+M8 门槛四态 + 失败升级循环 + 轮次快照 append-only
└── test_compliance_flow.py  # 每个脚本至少 2 条断言，接入现有 pytest
```

- **与 harness-demo 的关系**：那 9 个脚本讲"单个 Agent 怎么跑得稳"；这 4 个讲"一圈 Agent 怎么分工守门"。README 里互相引用。
- **为什么不用真 LLM**：模式的价值全在流程控制（状态机、闸门、计数、快照），规则式 FakeLLM 足够演示，且零成本、CI 可跑。
