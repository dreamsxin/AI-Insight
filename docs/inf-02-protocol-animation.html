01形状

同样是"你好"，嵌得深浅不同

字段名不一样，嵌套层数不一样 —— 但信息是同一份。

Chat Completions
messages[]
{ role: "user" }
{ content: "你好" }
{ tool_calls: [...] }
嵌套 2 层
Responses
input[]
{ type: "message" }
content: [ ... ]
{ type: "input_text" }
嵌套 4 层
Messages
messages[]
{ role: "user" }
content: [ blocks ]
{ type: "text" }
嵌套 3 层
如果每个后端都自己去解析这三种形状，就会有三份实现、三种 bug。
02汇流

先归一，再谈模型

三种请求，落到同一个 Conversation 结构上；后面的模板、分词、推理只写一遍。

Conversation · 统一结构
systemYou are a helpful assistant.
user你好
assistantreasoning + text + tool_call
这一层不产生任何智能，但它决定了后端能不能替换。
03零件

对话里只有四类标准件

协议再花哨，拆完还是这几样东西。

① 角色

system / user / assistant，决定这段话是谁说的。

role
② 内容片段

文本、图片、思考过程，按顺序拼在一条消息里。

content parts
③ 工具调用

函数名 + 参数，以及工具返回的结果。

tool call / result
④ 图片来源

base64 或外链，交给模型前统一预处理。

image ref
四类零件 + 顺序 = 一段完整对话。顺序丢了，模型就失忆了。
04模板

同一段对话，不同版本渲染出不同的字

模板由模型版本决定。V4 不吃图片，V4.1 才吃。

对话
user 你好，看这张图 image
→
V4 · 不接图片
<｜User｜>你好，看这张图 [Unsupported Image] <｜Assistant｜>
同一段对话
user 你好，看这张图 image
→
V4.1 · 支持图片
<｜User｜>你好，看这张图 <｜image｜> <｜Assistant｜>
图片被换成一行文字，不是报错 —— 降级也是一种兼容。
05回流

输出走的是同一条路，反过来

模型只吐 token。先解析成事件，再按各家协议分包。

一进一出，协议层就干这两件事：翻译与再翻译。

07为什么

这一层为什么值得用 Rust 重写

它不在 GPU 上跑，却站在每个请求的必经之路上。

⚡
一次遍历

转换、渲染、解析串成一条链路，不来回构造中间对象。

🐍
Python 只做绑定

Python 侧只拿到调用接口，重活留在 Rust 里。
