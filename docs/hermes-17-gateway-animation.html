STEP 2路由与降级

五种策略 + 一条备降跑道

LiteLLM 的五种路由策略：加权随机 / 用量最低 / 延迟最快 / 最闲 / 成本最低

allowed_fails 3 次 → 冷却 5s · 到期自愈
🎲simple-shuffle 加权随机分摊✓
📉usage-based 当分钟 TPM 最低者优先✓
⚡latency-based 响应最快 + 缓冲带防打满✓
💸cost-based 每 token 单价最低者优先✓
🔥main-lane 连续失败 3 次 → 冷却 5 秒✕ 冷却
✕ 主力供应商 429 限流 → 自动切换备降跑道：Anthropic → Gemini → 本地模型
RetryPolicy 按错误类型分别配重试 · 同组重试穷尽再跨组 fallback
💡 用户看到的只是「答出来了」—— 换了几条跑道他不知道
STEP 3密钥托管

真钥匙锁保险柜，员工只拿房卡

下游调用方拿「虚拟 key」—— 可注销、带限额；真实供应商密钥只存在网关里

虚拟 key 泄露 = 换一张卡 · 门锁不动
🔑真实供应商密钥 sk-ant-…（全部供应商）🔒 只存网关保险柜
🎫网关签发虚拟 key：sk-vt-team-a（带 tpm/rpm 限额 + 预算）发给大家用
📤Agent / 应用拿虚拟 key 调网关随时可注销
🛡️PII 过滤：Presidio 检测姓名/信用卡/邮箱 → MASK 替换或 BLOCK 拒绝可只扫一侧
泄露处理：注销虚拟 key、换一张即可 —— 真实门锁一个都不用换；Kong 的 Prompt Guard 还能抓越狱与注入
💡 密钥分级的意义：事故半径从「全部供应商」缩到「一张房卡」
STEP 4限流与成本

钱和速度，都在这里管

按 key / team / user 三级限流记账 —— 超额直接 429，不排队

max_budget + budget_duration 周期重置
🚦
限流配额

tpm_limit / rpm_limit / max_parallel_requests 按虚拟 key 生效；超限 429（不排队）—— 上层自己决定退避（11 期）

🧾
成本记账

每次调用自动按单价记美元，key → user → team 三级汇总入库，/key/info 随时查账

💣
反直觉：语义缓存对 Agent 是坑

同一问题换个措辞就命中「别人的答案」，而 Agent 每轮上下文都不同 —— 官方自己都警告别在 agentic 流量上开

精确缓存按整个请求体 hash —— 对话任何一点改动即 miss；多 worker 生产环境必须用共享 Redis
💡 网关是财务 + 保安 + 调度三合一 —— Agent 只管干活
