01窗口

每个字，只看最近一小段

滑动窗口注意力：窗口之外的历史，直接不看了。

很早以前刚说过正在写

窗口外的位置不存 KV，因为存了也用不上。
代价是：换一台机器、换一次请求，这段窗口就没了。

块缓存能按"前缀"复用，滑动窗口只能按"位置"复用 —— 这是麻烦的根源。
02麻烦

窗口是跟着位置走的

命中前缀之后，窗口里的内容已经和缓存对不上了。

缓存里的窗口
落在位置 2432–2560

上一次请求结束时的样子。

这次需要的窗口
落在位置 2690–2818

中间差了 130 个位置，缓存里那一段用不上了。

要精确重建，就得把 2560 个 token 重新过 20 层 —— 和从头算一遍差不多。
03办法

只往回看 128 步，够用

从第 s 个位置开始重放，但每个 query 只看自己前面一小段。

每往右挪一个位置，视野也跟着挪一格 —— 但永远只有 128 宽。
所以最前面的位置，看到的是 s 之后的开头，而不是更早的历史。

关键结论：重算成本从"跟上下文长度成正比"，变成跟窗口大小成正比。
04成本

一条陡线，一条平线

这就是"有界"两个字的全部含义。

横轴：上下文长度　纵轴：重算耗时
红色是精确重建，绿色是有界重放
上下文越长，这个差距越夸张 —— 长文档场景才真正吃得到这只红利。
05落盘

不是想存就存，只在 128 的倍数存

对齐之后，位置才对得上，复用才谈得上。

落盘规则
预留最后一个 token，向下取整到 128

不足一整个 128 单位，这一轮就不存。分片 prefill 中途也不存，只存最后一片。

解码期间
显存里单开一块"副本区"

每跨过 128 边界拷一份进去；请求结束时取最近一份。最多超 5 个 token，靠环形缓冲多出的 6 个位吸收。

20 层 × 134 token × 528 B ≈ 1.35 MB / 序列
一个序列的滑动窗口缓存只有 1.35 MB —— 所以它敢放在主机内存，而不是共享存储。
06两个用法

同一招，用在两处

一个是补窗口，一个是省掉整段 prefill。

编码器侧
块缓存照用，只补窗口

块缓存命中多少就用多少，不重算也不覆盖；只把命中前缀的最后 128 个 token 重跑一遍，专门重建窗口缓存。

解码器侧
把 2560 缩成 128

解码层的块缓存由最后一层编码层投影而来，只有窗口缓存要逐层算。精确重建要跑 2560 个 token × 20 层；重放只跑 128 个。

prefill 计算量近乎减半
重放出来的缓存只用于本次 decode，不进前缀缓存 —— 近似结果不该被传播。
07策略

命中多长，由两块缓存共同决定

块缓存说了算长度，窗口缓存说了算要不要退一格。

上限命中长度 ≤ L − 134（128 窗口 + 6 个投机回溯位）
第一步查块缓存，得到 L1（128 的倍数）
有窗口[L1−128, L1] 区间里有窗口缓存 → 命中 L1
没窗口回退到 L1−128，重算最后 128 个
退一格只损失 128 个 token 的重算，换来的是近似缓存的正确性。
08小结

少算的尽头，是"猜"

缓存让它不重复算，接下来是让它一次多算几个。

🪟
窗口不按前缀走

它跟着位置移动，所以块缓存那套直接复用的办法失效。

✂️
有界重放

只回放 128 个 token，且把视野截断在窗口内，成本变常数。

🎯
回退一格

窗口缺失时宁可少命中 128 个，也不传播不准确的缓存。
