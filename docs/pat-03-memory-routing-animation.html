STEP 3入库前两道闸

不够确定的不存，同一件事不堆

提取结果不是照单全收：置信度低于阈值丢弃；同一 key 的新值覆盖旧值，而不是并排堆三条

user.city = 杭州0.93 ✓
rule.ask_city_first = true0.86 ✓
user.dish = 好像随便0.38 ✕
置信度阈值 0.6 ↓ 丢弃（模型自己都没把握，别让它污染记忆）
同 key 去重 = 更新，不是追加
第 2 轮：user.city = 杭州　→　第 9 轮：user.city = 上海（已搬家）
user.city = 杭州 ⟶ 覆盖为 user.city = 上海，旧值进历史版本可回溯，但召回只取最新一条
💡 记忆库的敌人不是忘 —— 是低质量条目越攒越多，检索被噪音淹没
STEP 4三个抽屉，三种放法

记忆类型决定存哪、怎么查

三色不只是标签 —— 访问方式不同，落的存储也不同（工程上可简可繁，这里是典型形态）

📘
事实库
SEMANTIC

用户画像、偏好、稳定事实；按语义相似度召回

向量库 + KV 元数据
📒
时间线库
EPISODIC

「什么时候发生了什么」的事件与教训，按时间+主题取

SQLite / 文档表
📗
规则库
PROCEDURAL

「以后该怎么做」的规矩，少量、高优先级、几乎条条命中

规则配置 / prompt 片段
📌 procedural 最特殊：它常不经过检索，而是直接拼进系统提示词 —— 「先问城市」这类规矩值得每次都在场（ai-07 期：程序性记忆藏在提示词与代码里）
💡 别用一把锤子钉三种钉子 —— 查法决定存法
STEP 5用时怎么取

一个问题，三路各取所需

新问题进来先过 Memory Router 判断它需要哪类记忆 —— 不是把三库全捞出来，而是分流去取、汇合注入

query → router → semantic ║ episodic ║ procedural → 合并注入
🎤「周末想带爸妈吃顿清淡的，有推荐吗？」新轮对话开始，组装上下文前
🧭 ROUTER：需要口味偏好 + 城市 + 上次教训 + 用餐规矩
📘 semantic口味清淡 · 爸妈同行 · 城市=杭州
📒 episodic上次某店排队 1 小时，老人体验差
📗 procedural规矩：推荐餐厅先确认城市与人数
📥 去重 + 按预算裁剪后，拼成 <relevant-memories> 块注入本轮上下文（预算裁剪见 hermes-13 期）
写的时候三色分流，取的时候也三路分流再汇合 —— 这就是「记忆路由」：取数版的 Plan-and-Execute，先判断要什么，再动手找
💡 好记忆系统的关键不是存得多 —— 是该想起来的时候，恰好捞到那几条
