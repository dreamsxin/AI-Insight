缓存金字塔

算过的东西，
按"离 GPU 多远"分三层存着。

向下滚动↓
01三层

热的在显存，温的在内存，冷的在存储

不是所有 KV 都值得占显存，也不是所有 KV 都值得丢。

1HBM 显存在飞的块 + 状态缓存，引擎自己管最快
2主机内存滑动窗口 KV，单副本，跟着机器走跨机 400G 拉取
33FS 存储分页块 KV，全集群共享，容量最大最便宜
越往下越便宜、越慢、越大。命中哪一层，决定了这次省多少。
02选址

为什么不放本地盘

本地缓存会让"命中"和"均衡"打架。

放本地机

想让前缀命中，就得把请求发到"有这份缓存"的机器。
可负载均衡想把请求发给"最闲"的机器。
两件事互相拧着。

vs
放共享存储

任何一台 prefill 机都能命中任意前缀。
路由只看忙闲，不必看缓存在哪。

代价是每次命中都要走一次网络 —— 但至少不用二选一。
03命中

先算清命中多长，再决定发给谁

只查元数据，不搬 KV。这一步省不掉，但很快。

前缀哈希链
块 1块 2 块 3未命中

命中长度 = 连续命中的块数（按 128 token 对齐）
这个数字必须在路由之前拿到，所以它藏不掉。

其余环节都能异步重叠，唯独"算命中长度"站在关键路径上。
04搬运

取回 KV 的三段路

从存储到显存，不能一口气堵在路上。

3FS

单独进程异步拉

→
共享内存

先落主机内存

→
HBM

逐层换入

换入时用 GDR：让网卡直接读写显存，占用 PCIe 但不占 SM。
因为 CUDA 拷贝引擎处理这种细碎块很不划算。

目标是让"搬 KV"和"算前向"同时进行，而不是串起来。

06过期

留三天，还是七天

对话流量的命中是长尾的：少数 KV 被反复读很多次。

把 chatbot 的 TTL 从 7 天砍到 3 天，命中率只损失 0.5%–1%。
agent 流量则用 3 天。
这不是拍脑袋：长尾曲线在 3 天之后已经平得几乎看不出来。
07回收

谁负责删

缓存服务自己不判过期，交给存储层做。

存储节点上跑一个 GC Worker
按 LRU 驱逐最久没被读的块
压到水位线以下就停手
数据本身有 10+2 纠删码，容忍两台节点同时故障
缓存层不设 TTL 逻辑，只设"留多久"的策略 —— 删的活交给更懂磁盘的人。
08小结

块缓存有了，滑动窗口那部分呢

不是所有 KV 都适合按块存。

🏔️
三级介质

显存 → 主机内存 → 共享存储，按热度和成本分层。

📡
共享让路由自由

任何机器都能命中任意前缀，不必为缓存牺牲均衡。

⏳
TTL 是性价比题

3 天换回 99% 的命中率，剩下的长尾不值得再付钱。
