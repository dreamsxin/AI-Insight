看图、读题、写字，分开雇人

02为什么 VE 单独

图片的活，来得快去得也快

一张图进来，计算量瞬间冲高，然后长时间归零。

📥
按机器粒度路由

prefill 机随机挑一台带 VE 的机器，图片整张送过去。

🧮
按 patch 数选卡

同一台机器上，挑当前处理 patch 最少的那张卡。

💰
不必用最好的卡

单卡足够，便宜的卡反而更划算。

patch 数可以直接从宽高算出来：宽/patch × 高/patch，不需要先跑一遍。
03菜单

四种并行，各治一种病

别混着记，记住"它切开的是什么"。

TP
切一层里的矩阵

同一层拆到多卡，每步都要通信。带宽要求高。

DP
切请求

每卡跑完整模型，各管一批请求。最省心。

EP
切专家

MoE 的专家分到不同卡，token 飞过去算。本系列主角。

CP
切上下文

长序列按段拆开。这套系统暂时不用。

这套系统的选择很干脆：attention 用 DP，MoE 用 EP，TP 和 CP 都不上。
04配比

两段的要求，正好相反

prefill 要"刚好装下"，decode 要"越大越好"。

PREFILL
EP2–8
原则：HBM 允许的最小值
  • 不缺并行度
  • 缺的是别浪费卡
  • DP 2–8 同时开着
DECODE
EP64–128
原则：能开多大开多大
  • 卡越多，每卡搬的专家越少
  • 每步访存被摊薄
  • 这就是 Wide-EP
同一个模型，两段用了差一个数量级的并行度 —— 因为它们卡的地方不同。
05Wide-EP

卡越多，每张卡越"轻"

每步只激活一小撮专家。卡多了，分摊到每张卡上的专家权重就少了。

EP8 · 8 张卡，每卡守一大批专家 · 每步搬得多
EP64 · 每卡只守几个 · 每步搬得少
Wide-EP 买到的是每步显存流量的下降 —— 这正是 decode 的瓶颈。
06代价

宽，是有代价的

天下没有只赚不赔的并行。

🔗
通信域变大

从 8 卡扩到 64 卡，一次 all-to-all 的路更长、更容易堵。

💥
故障域也变大

64 卡是一个通信域，一张卡挂了整个实例不可用。

🧯
只能靠冗余兜底

重启要几分钟，所以靠配额冗余 + 请求重路由，而不是靠修得快。

重启时按当前健康卡数重新决定 EP 大小 —— 剩下的卡继续干活。
07最小单元

一套能跑的最小配置

P 和 D 的卡数大致 1:1，但 decode 起步就要 64 卡。

PREFILL · 64 卡
DECODE · 64 卡
1P≈ 1 : 11D
所以"最小高效部署单元"不是 1 台机器，而是 64 卡 prefill + 64 卡 decode。这也是为什么小规模自建很难复刻这套配置。
跨机房也可以：KV 被压得很小，P 与 D 分处相邻机房，按 8 卡 400 Gbps 预留互联。
08小结

拆开之后，问题变成"怎么排班"

机器分好了，接下来是谁先算、谁后算。

🧩
三段解耦

VE / Prefill / Decode 独立伸缩，两个延迟指标互不牵连。

📐
并行度按需

prefill 取最小够用，decode 取最大可用。

⚖️
宽度换流量

Wide-EP 用更大的通信域，换更低的每步访存。
