01差距

差在一段汇编

不是算法不同，是「少了一段手写 SASS」。

开源 FlashMLA
少一条手写 SASS 优化

decode 路径上少了一层指令级打磨，实测慢 5–10%。

DeepGEMM / 其它
大体一致

indexer 与 mega 系列有些差别，其余差异不大。

这类优化的特点是：手写汇编 → 只对某一个 kernel 有效，移植性差。

所以真正值得问的是：这么好的 10%，为什么端到端只剩 5%。
02摊薄

它只占一步的一部分

端到端时间里，attention 只是其中一块。

attention 26% MoE 42% 通信 21% 其它 11%
attention MoE 通信 norm / 采样 / 调度

占比为示意；即便 attention 慢 10%，摊到整步也只有约 2.6%。

实测端到端差 5%，说明差距不止 attention 一处 —— 但量级就是 5%。
03边际

再往里抠，越来越薄

同样的投入，换回来的端到端收益一路走低。

横轴 = kernel 层投入；纵轴 = 端到端收益。前段陡、后段几乎水平。

这不是「优化没用」，是优化的对象从「算」变成了「等」。
04怎么查

先看 trace，再决定改哪里

官方给的路径是：跑 benchmark，拿 trace，看 kernel 占比。

python examples/benchmark.py # 出 trace trace 里能看到： · 每类 kernel 的调用次数与耗时占比 · 启动之间的空隙 · 通信与计算是否重叠

先量再改：如果某类 kernel 只占 3%，把它优化一倍也只赚 1.5%。

这就是为什么「系统层」比「算子层」回报高 —— 它改的是占比大的那部分。
05所以

该往哪里投人力

kernel 层

回报低但确定：5% 就是 5%，而且一旦写成，长期有效。

调度 / 缓存

回报高且不稳：命中率与排队情况决定实际吞吐，能差出几倍。

并行 / 精度

结构性收益：EP 规模、位宽、分块策略，一动就是量级。

本系列第一季讲的调度、KV、EPLB，都属于第三类。

一句话：kernel 决定「上限」，系统决定「能不能摸到上限」。
