STEP 2错误是观察

报错塞回去，让它自己改

工具报错不等于主循环崩溃 —— 报错文本作为一条观察，塞回 messages（04 期）

messages.push({"role":"tool", "content": "Error: ENOENT…"})
工具报错read_file("config.json") → ENOENT: no such file
塞回循环报错文本进入 messages —— 模型「亲眼看到」了失败
下一轮自救ls 一看 → 文件叫 config.yml → 换名字重读 → 成功
普通程序遇到异常抛出去就完事；
Agent 的特权是：错误也是上下文，看一眼还能再来
💡 错误信息写得越详细，模型自救的成功率越高
STEP 3指数退避

被限流了，别急着再敲

网络抖动、429 限流 —— 立刻重试只会火上浇油，要等得越来越久

1s → 2s → 4s（+ 随机抖动）· 最多 N 次
💥 失败 ⏳ 等 1s ⏳ 等 2s ✓ 等完 4s 再试
🎲
加随机抖动（jitter） —— 一百个客户端同时退避、同时重试，会把服务器第二波打趴
♻️
先问幂等吗 —— 查询、读文件重发无害；「转账」「下单」类写操作盲目重试 = 重复扣款
💡 重试的礼貌：越挫越慢，并且只重试「重了也没事」的操作
STEP 4熔断与上报

重试穷尽，就体面认输

退避重试 N 次仍失败 —— 换条路（降级）或如实上报，绝不假装成功

MAX_RETRIES 用尽 → 降级 / failed 如实上报
job-03 · fetch_webpageMAX_RETRIES = 3
try-1超时 · 退避 1s✕ 失败
try-2429 · 退避 2s✕ 失败
try-3超时 · 退避 4s✕ 失败
终态不再重试 · 上报发起方⛔ failed
还有一条内部红线：04 期的 MAX_LOOPS —— 模型反复撞同一堵墙时强制叫停
最恶劣的失败是编一个「已完成」—— 宁可如实报错，不许谎报成功
💡 体面的认输：换条路走（07 期降级），或把失败原样说出口
STEP 5失败账本

每次挣扎，都记一笔

重试了几次、降级到哪条路、最终什么状态 —— 全部落账，事后可查

tool · error · attempts · final status
read_fileENOENT → ls 纠正文件名✓ 成功
http_get429 → 退避重试 ×2✓ 成功
search_api超时 ×3 → 切换备用源↻ 降级
deploy重试穷尽 · 上报发起方⛔ failed
这份账本向上汇入 07 期的批量汇总报告 —— 单任务的重试史，就是批量报告里的一行
💡 有了失败账本，「它当时到底卡在哪」才不再是一桩悬案
