一次调用的完整契约 · 逐屏动画演示

📋 tool_use ▶️ 执行 🔁 tool_result

「工具调用不是函数调用 —— 是一场严格配对的消息接力」

上滑逐屏观看▾
STEP 1id 配对

每个调用都是一张对账单

LLM 发出 tool_use（带唯一 id），Hermes 必须以同 id 的 tool_result 回填 —— 一次都不能错

tool_use.id ↔ tool_result.tool_use_id · 严格配对
发起tool_use · read_file({"path":"src/app.ts"})id: toolu_01A
执行Hermes 运行工具 → 得到结果…
回填tool_result · 内容 = 文件内容id: toolu_01A
id 对不上，请求会被 API 直接拒绝 —— 不是警告，是协议错误
中断、超时的调用也要补一条 error 版 tool_result，账本永远要平
💡 配对是协议的根 —— 有借必有还，借据就是 id
STEP 2schema 校验

参数是 JSON 文本，先验后跑

LLM 输出的参数本质是文本 —— 过一遍 JSON Schema 校验才轮得到执行

JSON → schema 校验 → 执行 / 打回重试
LLM 参数

{"path": "src/app.ts",
"encoding": "utf8"}

→
Schema 闸门

类型 / 必填 / 枚举
strict 模式硬校验（dev-01 期）

→
✓ 执行

或 ✕ 校验错误
作为 tool_result 塞回重试

校验失败不执行、把错误文本塞回循环 —— 模型下一轮自己就改对了（错误即观察，Hermes 11 期）
💡 闸门在代码里 —— 模型给的参数，永远当不可信输入
STEP 3并行调用

一条消息，可以带好几个调用

没有依赖的调用可以并行发 —— 但回填必须按原序、一个不少

assistant 消息内 3 × tool_use → 3 × tool_result
read a.ts
read b.ts
read c.ts
⇉ 并行执行
3 × tool_result 按原序回填
⇇
结果 a
结果 b
结果 c
并行的前提是无依赖：后一个调用要用前一个的结果，就必须等 ——
让模型学会「能并行就并行」，回合数直接减半
💡 并行发、按序收 —— 省的是轮数，也就是钱
STEP 4流式拼接

参数是分块到的，拼完才能跑

流式响应里 tool_use 的参数不是一次到齐 —— JSON 片段增量到达，拼完整才可执行

input_json_delta：{"pa + th": "s + rc/app…" → 拼合
STREAM · input_json_delta 逐片到达
{"path": "src/app.ts","line": 12}
✓ 拼合完整 → {"path": "src/app.ts", "line": 12} → 执行
执行期没有新 token，流会「静默」但 ping 心跳不断（10 期）——
拼接逻辑写错一个边界，参数就是残缺 JSON，这也是自研 Agent 常见的隐性 bug
💡 别在半截 JSON 上调工具 —— 先拼合、再校验、后执行
STEP 5顺序状态机

合法顺序只有一条线

messages 里的角色交替有硬规则 —— 违反任意一条，请求整包被拒

assistant(tool_use) → user(tool_result) → assistant…
✓assistant 发出 tool_use（1 个或多个）
✓user 回填 全部 对应的 tool_result
✓assistant 继续说话或再发调用 —— 循环往复（04 期）
✕tool_result 丢了一个 id → 协议错误，请求被拒
✕assistant 连说两轮、中间不回填 → 同样被拒
把这套状态机写进代码（而不是靠感觉拼 messages）——
自研 Agent 一半的「玄学报错」，根源都在顺序和配对上
💡 协议不玄 —— 是状态机；照着状态机写，报错自然消失
RECAP全景

一张对账单走完全程

发起（id）→ 校验（schema）→ 执行（可并行）→ 回填（同 id 按序）→ 再循环

tool_use 发起→schema 校验→并行执行→拼合参数→同 id 回填
🧾
id 是对账凭证

tool_use 与 tool_result 严格配对，中断也要补 error 结果 —— 账本永远要平

🚧
参数当不可信输入

schema 校验失败不执行、错误塞回循环 —— 模型下一轮自己改（dev-01 / Hermes 11 期）

⚙️
协议即状态机

合法顺序只有一条线 —— 照状态机写代码，玄学报错消失一半
